# 모듈 분리 경계 관리

## 핵심 원칙 — 손으로 관리하는 목록은 반드시 낡는다

2026-08-24 실측: 블로그 모듈은 2026-08-18에 "분리 경계" 목록을 문서에
적어뒀는데, 6일 만에 어긋나 있었다.

- 목록에 **없는데 필수**인 파일 3개 (`blog_publish_manual.py`(주 발행 경로),
  `blog/core/writer.py`(에디터 자동화 본체), `blog/management/post_cache.py`)
- 목록에 **있는데 못 쓰는** 파일 1개 (`blog_ai_batch_20.py` — GPT 차단)

그래서 **목록을 믿지 말고 import를 스캔**한다. 문서는 사람이 읽는 용도,
판정은 도구가 한다.

## 점검 실행

```bash
python -m scripts.naver.blog.cli.check_blog_separability          # 리포트
python -m scripts.naver.blog.cli.check_blog_separability --strict # 위반 시 exit 1 (CI용)
```

출력 3종:
1. **타 업무 도메인 import** — 0건이어야 함(격리 규칙 위반)
2. **앱 본체(`ai_orchestrator`) 의존** — 있으면 분리 시 손봐야 할 목록
3. **목록에 있으나 실제로 없는 경로** — 문서 낡음 신호

## 판정 기준 3단계

| 등급 | 조건 | 의미 |
|---|---|---|
| ✅ 분리 가능 | 타 도메인 0건 + 앱 의존 0건 | 폴더째 복사하면 됨 |
| ⚠️ 조건부 | 타 도메인 0건 + 앱 의존 N건 | 그 N건만 처리하면 됨 |
| ❌ 불가 | 타 도메인 import 존재 | 격리 규칙 위반 — 먼저 고쳐야 함 |

**블로그 모듈 현재 상태(2026-08-24)**: ⚠️ 조건부 — 타 도메인 0건,
앱 의존 1건(`naver_kin_client`, 범용 커넥터라 함께 복사하면 됨)

## 의존이 발견됐을 때 — 3가지 선택지

1. **자체 구현으로 대체** — 코드가 짧고 범용이면 이게 낫다.
   실례: `images.py`의 `ai_orchestrator.config.get_local_data_dir`는
   환경변수 읽는 4줄짜리라 그대로 옮겨 심었다(동작 동일 확인 필수).
2. **함께 복사할 공용 인프라로 문서화** — 도메인 중립이고 덩치가 있으면
   중복 구현하지 말고 목록에만 넣는다.
   실례: `naver_kin_client.py`(84줄, 지식iN 검색) — 블로그 전용이 아님.
3. **어댑터로 교체** — 분리 시점에 인터페이스만 맞춰 갈아끼운다.
   실례: `scripts/auth/credentials.py`(자격증명) — 지금은 공용 재사용이 맞고,
   분리할 때 이 부분만 바꾼다.

**하지 말 것**: 분리를 위해 미리 코드를 중복 복사하는 것. 유지보수 지점이
둘로 갈라져 더 나빠진다. 실제로 필요할 때 옮긴다.

## 다른 도메인에 적용하려면

`check_blog_separability.py`를 복사해 상수 3개만 바꾼다:

```python
BLOG_PATHS        = [...]   # 이 도메인의 파일·디렉터리
FORBIDDEN_DOMAINS = [...]   # 참조하면 안 되는 타 도메인
APP_PREFIX        = "ai_orchestrator"
```

`CLAUDE.md`의 "의존성 방향" 규칙(서로 다른 업무 도메인 간 직접 import 금지)이
이미 있으므로, 도메인별 점검 도구는 그 규칙을 파일 단위로 구체화한 것이다.

## 언제 돌리나

- 그 도메인에 **새 모듈을 추가한 직후** (오늘처럼 4개 추가하면 반드시 어긋남)
- 분리를 실제로 검토할 때
- 문서의 분리 경계 목록을 갱신할 때 — **도구 결과를 문서에 반영**하지,
  문서를 보고 도구를 고치지 않는다
