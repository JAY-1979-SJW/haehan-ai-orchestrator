# 블로그 작업 재개

## 왜 필요한가

블로그는 2개 계정(skyjwsin 건설, skyjwshin 조명)을 별도로 운영하고,
각각 코드 위치·발행 기준·CTA 정책·해결된 버그가 다르다. 세션마다
`git log`나 코드를 처음부터 뒤지면 이미 해결한 문제를 다시 겪거나
(예: 커스텀 주소 하이픈 버그, edit_post 이미지 소실 버그), 이미 확보한
리서치 결과를 놔두고 새로 만들려 든다.

## 실행 순서

1. **어느 계정 작업인지 먼저 확인** — 사용자 발화에 "조명"·"반딧불"이
   있으면 skyjwshin, "건설"·"적산"·"공무"면 skyjwsin. 애매하면 사용자에게 묻는다.

2. **해당 계정의 작업기록 메모리를 먼저 읽는다** (탐색보다 먼저):
   - skyjwsin → `channel-naver-blog-worklog.md`
   - skyjwshin(조명) → `channel-naver-blog-lighting-worklog.md`
   - 공통/구조 → `MEMORY.md`의 "채널별 작업기록" 섹션 전체

3. **기록에 있는 "다음(미착수)" 항목부터 사용자에게 확인** — 이전 세션이
   끝난 지점을 그대로 말해준다. 예: "지난번엔 skyjwshin 71개 리서치
   주제 중 1편만 발행했고, gonobi 제품사진→GPT 상세페이지 건은 형태를
   못 정해서 멈췄습니다. 어디부터 할까요?"

4. **기록에 적힌 "실제로 겪은 함정"을 재확인 없이 신뢰한다** — 예를 들어
   skyjwshin의 커스텀 주소(`beautiful-light`) 하이픈 버그는 이미
   `writer.py`/`publish.py`/`blog_publish_manual.py` 3곳 다 고쳐져
   있다. 다시 재현해보거나 의심하지 않는다. 단, "메모리는 시점 스냅샷"
   원칙대로 — 코드를 실제로 실행하는 시점에 결과가 기록과 다르면
   (예: 이미 고쳤다는 버그가 재발) 메모리를 갱신한다.

5. **작업이 끝나면 반드시 해당 작업기록 메모리를 갱신한다** (아래 참조).
   이 스킬은 "읽기"만이 아니라 "쓰기"까지 포함한 왕복 루틴이다.

## 작업기록 갱신 규칙 (매번 세션 끝에)

- **현재 상태 표**(누적 발행 수, 최근 log_no 등)를 최신값으로 갱신
- **새로 겪은 함정**은 "실제로 겪은 함정" 섹션에 원인+해결을 한 문단으로
  추가(코드 커밋 해시나 파일명을 함께 적어 나중에 대조 가능하게)
- **다음(미착수) 목록**을 갱신 — 끝난 항목은 지우고, 새로 생긴 미완료
  작업을 추가
- 절대 하지 말 것: 코드 패턴이나 파일 구조를 그대로 베껴 적기(코드를
  읽으면 알 수 있는 것) — "왜/무엇이 달랐는지"만 남긴다

## 메모리 파일이 없는 새 채널이면

이 패턴(`channel-{계정}-worklog.md`)으로 새로 만들고 `MEMORY.md`의
"채널별 작업기록" 섹션에 한 줄 추가한다. 기존 두 파일의 구조(현재 상태
표 → 코드 위치 → 함정 → 발행 이력 → 다음)를 그대로 따른다.
