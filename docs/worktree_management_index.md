# Worktree Management Index

Updated: 2026-05-13

This document defines how the current dirty worktree is classified and managed. The source of truth is generated by:

```powershell
python scripts\ops\worktree_change_index.py
```

The generated JSON is written to `data/worktree_change_index_latest.json` and groups changes by git status, architecture layer, owner, and review category.

## Mandatory Pre-Work Rule

Before starting any new task, regenerate the worktree index:

```powershell
python scripts\ops\worktree_change_index.py
```

Then record pre-change dry-run evidence for the selected scope before editing
code:

```powershell
python scripts\ops\pre_change_dry_run.py --scope <scope> --reason "<why>" -- <dry-run command>
```

Then pick one scope for the task:

- `owner`, for example `hiworks`, `eum`, `naver`, `platform`, `docs`
- `category`, for example `site_automation`, `contract_or_policy`, `active_code`, `test`
- `layer`, for example `L5` site module or `L7` audit/persistence

If the selected scope already has changed files, inspect those files before editing. Treat them as existing user/context changes and work with them. Do not revert unrelated changes.

## Error Or Uncertainty Rule

When a task fails, a test breaks unexpectedly, or the next step is unclear:

1. Regenerate the worktree index.
2. Find the failing file in `data/worktree_change_index_latest.json`.
3. Check its `owner`, `category`, and `layer`.
4. Consult the reference pack below before changing direction.
5. If the issue touches deploy paths, record a dry-run before commit/deploy.

Reference pack:

| Situation | Reference |
| --- | --- |
| Common operating order across all sites | `docs/common_operations_index.md`, `configs/common_operations_index.json` |
| Worktree ownership or staging decision | `docs/worktree_management_index.md` |
| Layer or module boundary decision | `docs/layer_classification.md` |

| Site completion status | `docs/site_automation_status_index.md` |

## Review Categories

| Category | Meaning | Commit handling |
| --- | --- | --- |
| `contract_or_policy` | Shared schemas, configs, gates, policy, security | Review first. Requires docs/tests when behavior changes. |
| `site_automation` | Site modules and business workflows | Keep site-scoped. Requires matching tests or logic reference docs. |
| `audit_or_persistence` | DB, logs, audit, operations tooling | Check schema/log format compatibility. |
| `active_code` | General active code outside a site module | Review before staging. Avoid mixing with unrelated site work. |
| `test` | Unit, policy, fixture, smoke tests | Stage with the code it proves. |
| `doc_or_archive` | Design docs, reports, archived probes | Stage with the change they explain. |
| `runtime_artifact` | Generated data, logs, downloads, screenshots | Keep out of commits unless promoted as evidence. |
| `local_pc_automation` | Excel/HWP/CAD/local machine automation | Verify path/backup/approval boundaries. |
| `app_surface` | API server or UI surface | Requires focused tests and, for deploy paths, dry-run evidence. |

## File Placement And Promotion Standard

Use this standard when creating or tidying files in the dirty worktree.

| File kind | Default location | Commit rule |
| --- | --- | --- |
| Active site code | `scripts/<site>/` | Stage only with matching tests or logic reference updates. |
| Shared policy, schemas, security, config | `scripts/`, `configs/`, `security_utils.py`, `logging_utils.py` | Review first; behavior changes need tests/docs. |
| Generic browser or form helpers | `scripts/explorer/`, `scripts/form/`, `scripts/cdp_*.py`, `scripts/page_helper.py` | Keep reusable; site selectors stay in `scripts/<site>/`. |
| One-off debug/probe scripts | `scripts/archive/debug/` | Do not keep at repo root unless intentionally active. |
| Operator handoff notes | `docs/reports/` or root `HANDOVER_*.md` | Convert durable knowledge into reference docs before commit. |
| Runtime evidence | `data/`, `tmp/`, `logs/`, `runs/`, `storage/` | Local only by default; promote curated evidence to `docs/reports/` or `tests/fixtures/`. |
| Reproducible test fixtures | `tests/fixtures/` | Add explicit `.gitignore` exception when a fixture is intentionally tracked. |

Promotion means moving information from a runtime artifact into a stable review
target, not blindly committing generated files. For example, summarize
`data/<site>_*_latest.json` into `docs/reports/<site>_...md`, or reduce it into
a deterministic fixture under `tests/fixtures/`.

## Existing Worktree Triage

For the current large worktree, use this order:

1. Keep `runtime_artifact` out of commits unless explicitly promoted.
2. Review `contract_or_policy` first because it affects gates, schemas,
   security, and common indexes.
3. Review one site owner at a time: `eum`, `hiworks`, `naver`, `google`,
   `smartstore`, then `g2b`.
4. Archive or relocate root-level one-off scripts such as `debug_*.py`,
   `check_*.py`, `close_*.py`, and `list_tabs.py` only after confirming they
   are not active entry points.
5. Treat deleted files as intentional only after checking whether an equivalent
   file exists under `scripts/archive/` or a focused site module.

## Management Rules

1. Do not revert unrelated existing user changes.
2. Treat `runtime_artifact` as local evidence by default.
3. Site work must include a site logic reference or completion report once it reaches `complete_baseline`.
4. Existing active code changes are blocked by the quality gate unless explicitly approved with `--allow-existing-code-change`.
5. Deploy-related changes require `scripts\ops\deploy_dry_run.py` evidence before commit or deployment.

## Current Operating Flow

1. Generate the worktree index before starting.
2. Check `docs/common_operations_index.md` for the selected owner and next action.
3. Record pre-change dry-run evidence for the selected scope.
4. Work within one owner/category at a time, for example `owner=hiworks`.
5. Run targeted post-change tests for that owner.
6. Update the site/status/document index.
7. Run the quality gate before staging or deployment.

## Full Business Workflow Rule

For business automation, implement complete workflows through:

```text
discover -> plan -> prepare -> approval -> execute -> verify -> log
```

The execute path must be developed, but state-changing execution must be
blocked until the user approves the prepared artifact. This applies to Google,
Naver, Hiworks, EUM, SmartStore, and all future site work.
