# 토큰 효율 구조 — AI 가 적게 읽고 정확히 일하도록 프로그램 구조 자체를 바꾼다 (2026-09-24)

```yaml
spec:
  id: token-efficient-architecture
  status: planned
  files:
    add:
      - tools/code_map/query.py
      - scripts/ops/agent_brief.py
      - configs/agent_roles.json
      - tools/hooks/agent_usage.py
```

## 문제 (2026-09-24 실측)
- 서브에이전트 20여 개 × 10만~28만 토큰. 토큰 ≈ (도구 호출 수) × (그때까지 쌓인 맥락) — 큰 파일을 읽을수록·호출이 많을수록 폭증.
- 원인이 **구조**에 있다: AI 가 알아야 할 정보가 거대한 단일 파일(`map.json`, `module_registry.json` ≈2만 줄, 검증 JSON)에만 있어 매번 통째로 읽거나 grep 해야 한다. 기계적 작업(라벨 적용·목록 생성)도 AI 가 손으로 한다. 역할별 모델이 설계에 없다.
- 사용자 지시: "위 내용을 설계상으로 반영 — 프로그램 자체 설계 구조를 변경".

## 원칙
1. **AI 는 답만 받는다** — 원자료(대형 JSON·로그)를 읽지 않고, 질문에 맞춰 잘라 주는 조회 도구의 짧은 결과만 받는다.
2. **기계적 작업은 스크립트** — AI 는 판단·설계·코드 수정만. 적용·집계·목록화는 명령 한 줄.
3. **모든 출력은 요약 먼저** — 표 1개 + "자세히는 파일 경로". 세부는 필요할 때만 조회.
4. **역할별 모델은 설정 파일이 정한다** — 사람(AI)의 기억이 아니라 파이프라인이 강제.
5. **사용량을 잰다** — 작업마다 토큰을 기록해 비싼 단계를 숫자로 찾는다.

## 구조 변경
| # | 지금 | 바뀐 구조 |
|---|---|---|
| 1 | `map.json`(수 MB) 통째 읽기·grep | `code_map/query.py` — `who-imports <파일>`, `imports-of`, `module-of`, `violations --module X`, `impact <파일들>`, `tests-for <파일들>` 등 **질문형 조회**, 결과는 수십 줄 |
| 2 | `module_registry.json` 단일 2만 줄 | **모듈 카드 단위 분할** `configs/module_cards/<모듈>.json`(소속·층·연결·데이터) — 작업 대상 모듈 카드만 읽는다. 전체 정본은 카드에서 생성(생성물) |
| 3 | 에이전트에게 긴 지시문 + "파일을 찾아 읽어라" | `agent_brief.py <spec-id> [--files …]` — 작업에 필요한 것만 담은 **작업 브리프**(대상 파일 목록·해당 모듈 카드·영향 테스트·금지 파일(WIP)·검증 명령·이전 결함 요약)를 1개 파일로 생성해 에이전트는 그것만 읽고 시작 |
| 4 | 검증 결과를 사람이 긴 출력에서 읽음 | verify_change·skeleton_gate·spec_trace 모두 **요약 1표 + 새 문제만** 출력(이미 부분 적용), 원자료는 파일로만 |
| 5 | 역할별 모델을 그때그때 지정(리뷰가 최상위 모델로 돈 사고) | `configs/agent_roles.json` — 역할→모델·도구 호출 상한·입력(브리프)·출력 형식. 예: 구현=sonnet, 리뷰=sonnet, 단순 대조=haiku, 설계 판단·사용자 보고=메인. 파이프라인 스크립트가 이 표로 에이전트 지시문을 만든다 |
| 6 | 라벨 적용·목록 정리·정본 맞춤을 에이전트가 수작업 | 스크립트화: `registry_sync --fix`(완료), 라벨 적용 `code_map/relabel.py --from <근거표>`, 삭제 목록 갱신 `deleted_index.py` 등 — AI 는 근거표(판단)만 작성 |
| 7 | 사용량 모름 | `agent_usage.py` — 작업(기준서 id)별 에이전트 토큰·도구 호출 수를 `data/ops/agent_usage.jsonl` 에 기록, 단계별 합계 보고. 기준서에 예산(`budget_tokens`)을 적으면 초과 시 경고 |
| 10 | **메인 세션이 직접 작업**(파일 수정·긴 파일 전체 읽기·긴 출력 열람) → 가장 비싼 모델의 가장 긴 맥락에 누적(이 세션 14.7MB의 주원인) | **메인 = 지휘만**(사용자 지적: "서브에이전트 새 세션 작업을 여기서 해야 하는데 안 된 게 더 문제"): 메인은 대화·판단·설계·승인·브리프 작성·에이전트 투입·요약 열람·스크립트 한 줄(병합 등)만. 코드 수정(1줄 포함)·파일 열람·테스트·검증 실행·리뷰·인계 작성은 전부 새 서브에이전트. 메인은 파일 전체 읽기 금지, 명령 출력은 요약 표만. 새 세션 강제(session_guard)는 안전망 |
| 9 | 서브에이전트를 SendMessage 로 계속 이어 씀(OpenAI 삭제 에이전트 3회 재개 — 매번 긴 기록 재독) · 한 에이전트가 도구 100회+ | **서브에이전트도 새 세션 원칙**(사용자 지시): ① 이어 쓰기 금지 — 수정·재작업은 새 에이전트 + 브리프(지적 사항·바뀐 파일만) ② 역할표에 도구 호출 상한(예: 구현 40, 리뷰 25) ③ 상한 도달 시 에이전트가 인계 파일(한 일·남은 일·주의) 작성 후 종료 → 새 에이전트가 인계 파일로 이어받음 ④ 호출 100회급 작업은 처음부터 단계로 쪼개 순차 투입 |
| 8 | 한 세션에 설계·시공·검증이 계속 쌓임 | **단계 경계 = 세션 경계**: 단계가 끝나면 인계 파일(`data/impact/<spec-id>.handoff.md`: 결과·남은 일·결정 사항) + 메모리 갱신 → 다음 단계는 새 세션에서 인계 파일로 시작 |

## 기대 효과 (추정 — 적용 후 7번으로 실측해 검증)
- 에이전트 1회 투입 토큰: 10만~28만 → 수만 수준(대형 파일 미열람·호출 수 감소)
- 리뷰 비용: 최상위 모델 → sonnet
- 메인 세션: 단계별 새 세션으로 누적 맥락 제거

## 판매 키트와의 관계
비개발자 고객도 AI 비용이 곧 운영비다. "적게 읽고 정확히 일하는 구조"는 키트의 핵심 차별점 — 조회 도구·브리프·역할표·사용량 기록을 공용 스킬에 포함.

## 단계
1. `code_map/query.py` + `agent_brief.py` + `configs/agent_roles.json` (가장 효과 큼)
2. 파이프라인 지시문 생성을 역할표 기반으로 전환, `agent_usage.py`
3. 모듈 카드 분할(모듈 카드 v2 결과 사용 — 변경 영향 게이트 설계와 같은 산출물)
4. 기계적 작업 스크립트화(relabel 등), 단계 인계 파일
각 단계는 기존 파이프라인(브랜치→검증→리뷰→병합) 적용. 역할표·조회 도구는 변경 영향 게이트(docs/specs/2026-09-24_change_impact_gate.md)의 드라이런에도 그대로 쓰인다.
