> 상태: 방향 확정 단계(1단계 — "목적 vs 현재상태" 대조 샘플). **코드 미작성, 커밋 없음.**

## 0. 왜 이 문서가 필요한가

`README.md`가 "3단계: 화이트리스트 실행기(저위험 read_file/list_dir만 실행 가능)"라는
**아주 초기 개발 단계**를 그대로 설명하고 있다 — 오늘 실측 확인한 실제 앱과 완전히
다르다. 즉 "이 앱이 뭘 위한 앱인지" 판단할 신뢰 가능한 기준 문서가 없었다. audit-kit 같은
구조 스캔 도구는 "현재 코드가 어떻게 생겼는지"만 보여줄 뿐 "무엇을 위해 그래야 하는지"는
모른다 — 그 목적을 이 문서가 먼저 정리한다.

## 1. 목적 (오늘 대화 + 기존 산출물 종합)

### 1.1 사용자가 명시적으로 확인한 우선순위 (오늘 발화 순서대로)

| 우선순위 | 내용 |
|---|---|
| P0 | "브라우저 연동을 사용자가 쓰기 좋게" — 자동화 **엔진**이 있어도 **사람이 실제로 쓸 수 있는 연결**(버튼→동작→결과)이 없으면 의미 없다는 원칙 |
| P1 | 개인 메일함(Gmail→네이버 순) AI 비서 — 업계 표준(승인 후 발송)과 일치 확인됨 |
| P1 | 건설 4개 프로젝트(g2b·견적·cad·EUM) + 메일 알림 연동 — 별도 마스터 문서(`2026-09-29_construction_ai_agent_direction.md`)로 이미 방향 확정, 사용자 승인: "1번으로 하자 그리고 메일함을 연결하고" |
| P2 | UI 품질 — "잘 만들었으면 좋겠다", 업계 표준 스택(Next.js+Tailwind+shadcn/ui) 확인 후 도입 승인 |
| 원칙 | 범위는 항상 작게 — "너무 일이 많은거 아닌가" 직접 지적, 매번 축소해서 진행 |

### 1.2 이 앱이 실제로 하는 일 (README와 달리 오늘 코드로 실측 확인)

haehan-ai-orchestrator는 더 이상 "화이트리스트 실행기"가 아니라, **로컬 PC의 CDP
브라우저 세션을 통해 여러 외부 서비스를 사람 대신/사람과 함께 조작하는 개인·업무
자동화 허브**다:

- 구글 생태계(Gmail 읽기/회신/AI초안, Calendar, Drive, Docs, Sheets, YouTube Studio, GCP)
- 네이버 생태계(블로그, 카페, 스마트스토어, 메일 수집·분석, 검색)
- 건설 도메인(EUM 장비 임대 22현장 실운영, g2b 입찰공고, 견적, CAD 연동 예정)
- 기타(하이웍스, 가비아, G2B, 인스타그램 등 사이트별 모듈 다수)
- 이 모든 것을 **Electron 데스크톱 셸**(admin-web을 webview로 감싸고 로컬 CDP를
  관리) + **FastAPI 서버**(L8) + **admin-web(Next.js)**(L9) + **run_claude_agent**
  (헤드리스 Claude Code 오케스트레이션 엔진)로 묶는다.

### 1.3 핵심 설계 원칙 (P0에서 도출, 오늘 반복 확인됨)

> **"버튼 뒤에 진짜 동작이 있는가"가 이 앱의 1급 품질 기준이다.**

오늘 실측: admin-web 버튼 대부분이 죽은 링크였다(Explore 조사 "실제로 CDP 브라우저를
움직이는 버튼이 하나도 없었다"). 제가 오늘 만든 것(Gmail 조회/AI비서, 구글도구 7종)이
전부 "이미 있던 백엔드 능력 + 없던 버튼 연결"이었다 — 즉 이 앱의 만성적인 문제는
**엔진과 UI 사이의 배선 누락**이다. 구조 재설계는 이 문제를 구조적으로 막는 걸
목표로 해야 한다(예: 신규 백엔드 기능 추가 시 "연결된 버튼 없음" 상태로 방치되지
않도록 하는 체크).

## 2. 현재상태 (audit-kit 구조 도구 기준)

### 2.1 레이어 구조 (`configs/module_registry.json`, 이미 잘 잡혀있음 — 유지)

```
L1 공용계약 · L2 정책/게이트 · L3 외부연동 커넥터 · L4 브라우저엔진 · L5 사이트모듈
L6 업무흐름 · L7 저장/감사 · L8 서버API · L9 화면(admin-web) · L10 로컬에이전트
L11 테스트 · L12 문서/운영도구
```
`skeleton_gate.py`가 커밋마다 강제 — 이 뼈대 자체는 건강하다. **문제는 레이어 안의
내용(특히 L9 화면)이 목적에 안 맞게 자라났다는 것**이다.

### 2.2 L9(admin-web) 구체적 문제 (오늘 발견)

`admin-web/src/app/ops/page.tsx` 1개 페이지에 성격이 다른 패널 12개가 그대로 쌓여있다:

| 패널 | 실제 성격 |
|---|---|
| OpsDashboard, ApiStatusBanner, SafetyPolicyBanner | 시스템 상태 |
| ApprovalQueue, WebTaskPanel, ExternalWebTaskSummary | 승인/작업 큐 |
| AgentStatusPanel, IntegrationStatusPanel | 에이전트/연동 상태 |
| AuditEventTable | 감사 로그 |
| GmailInboxPanel, MailAssistantPanel, GoogleToolsPanel | **업무 자동화 실행**(오늘 추가) |
| WorkTradeBoard, QuotePanel | 견적/거래(건설 도메인) |

**"운영 상태를 보는 화면"과 "실제 업무를 실행하는 화면"이 섞여있다** — 사용자가
지적한 "항목에 모든게 있으니 안됨"이 정확히 이 지점이다.

## 3. 목적 대비 구조 gap (핵심)

| 목적 | 현재 구조가 막는 지점 |
|---|---|
| P0: 버튼 뒤에 진짜 동작 | L9가 "상태 화면"과 "실행 화면"을 구분 안 해서, 새 자동화를 추가해도 어디 둘지 기준이 없다 → 그냥 ops에 쌓임 |
| P1: 업무 자동화(메일/건설) 확장 | 위와 동일 — 도메인별 화면 분리가 없어 앞으로 늘어날수록 ops 페이지가 계속 커짐 |
| P2: UI 품질 | 컴포넌트 라이브러리 없이 패널마다 손으로 버튼/카드를 다시 만듦 → 일관성 없음 |

## 4. 재설계 방향 (제안)

### 4.1 admin-web 메뉴를 "상태"와 "실행"으로 분리

```
[운영센터]  — 상태만(기존 OpsDashboard/ApprovalQueue/AgentStatus/Integration/Audit)
[메일 비서] — Gmail(+추후 네이버) 조회/AI초안/발송
[구글 도구] — Calendar/Drive/Docs/Sheets/YouTube/GCP
[건설 파이프라인] — WorkTradeBoard/QuotePanel(+ 2026-09-29 건설 마스터 문서 연동 시 확장)
```
각 메뉴는 Next.js 라우트(`admin-web/src/app/<도메인>/page.tsx`)로 분리 — L9 안에서
도메인별 하위구조를 만드는 것이라 L1~L8 레이어 규칙과 충돌 없음.

### 4.2 신규 자동화 추가 시 규칙(재발 방지, P0 구조적 보장)

새 백엔드 기능(L3~L8) 추가 시 "이 기능을 실행하는 admin-web 버튼이 어느 메뉴에
속하는지"를 함께 명시하도록 CLAUDE.md "신규 코드 위치 규칙"에 1개 항목 추가 제안
(§5.3 참고, 이번엔 문서화만 — 강제 게이트화는 2단계 논의).

### 4.3 UI 컴포넌트 표준화 (P2)

`admin-web`에 shadcn/ui 도입 — 이번 신규 화면(메뉴 분리 작업)부터 적용, 기존 패널은
점진 교체. 기존 Tailwind 유틸리티 클래스 방식과 공존 가능(shadcn는 Tailwind 위에서
동작).
