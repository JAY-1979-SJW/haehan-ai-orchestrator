# 건설전용 AI 에이전트 — 방향 확정 기준서 (2026-09-29)

> 상태: 방향 확정(사용자 승인: "1번으로 하자 그리고 메일함을 연결하고"). 이 문서는
> **총괄(마스터) 기준서**다 — 프로젝트 4개가 워낙 크고 각자 독립 저장소라, 각 프로젝트별
> 상세 구현 기준서는 별도 세션·별도 문서로 나눈다(§6). 이 문서는 "무엇을 왜 어떻게
> 엮을지"의 방향만 확정한다. 코드 미작성, 커밋 없음.
> 이전 문서 `docs/specs/2026-09-29_ops_automation_buttons_representative_flows.md`의
> "대표 버튼" 방향(블로그/카페/인스타/유튜브/구글/스마트스토어)은 이 문서로 **대체**된다 —
> 건설 도메인에 집중하기로 사용자가 방향을 좁혔다. 다만 그 문서 §3(버튼→`run_claude_agent`
> 메커니즘)은 그대로 재사용한다.

## 0. 결정된 방향

**범위**: 4개 프로젝트 전부 연동(§1의 "1번" 선택) + 메일함 연결(신규 추가).

```
[05. g2b]              입찰공고 발견·분석 (나라장터 공식 API, 25GB·투찰자 200만건, 실서버 운영)
        ↓
[09. 견적 프로그램]     견적 산출 (일위대가·품셈·자재DB·자재단가)
        ↓
[03. cad-program]       도면·설계 작업
        ↓
[01. haehan-ai-orchestrator — EUM]  낙찰 후 장비 조달·현장 모니터링 (실제 임대 22현장 운영 중)
        ↓
[메일함]  새 공고 발견 시 사람에게 알림 (신규 연결 대상)
        ↓
[사람]   최종 투찰·전자서명·제출 — 이 앱 생태계 전체가 여기만 자동화 안 함(g2b README에
         이미 코드 레벨로 BLOCKED)
```

**haehan-ai-orchestrator의 역할**: 4개 프로젝트를 대체하지 않고, 오늘 만든 CDP/MCP/
`run_claude_agent` 오케스트레이션 엔진으로 **지휘소** 역할만 한다 — 각 프로젝트는 그대로
독립 운영, haehan-ai-orchestrator가 Bash로 각 프로젝트의 기존 CLI/API를 호출해 묶는다.

## 1. 각 프로젝트 실측 요약

### 1.1 `05. g2b` (저장소명 `g2b-fire-bid`) — 가장 성숙
- 나라장터 공식 API 키 이미 발급·설정됨(`G2B_API_KEY_BID` 등, `.env`)
- `api_server.py`(FastAPI): `GET /search`(입찰공고) · `/result`(낙찰결과) · `/plan`(발주계획)
- **실측 검증(2026-09-29, 로컬 8000번에 직접 띄워 호출)**: `/search?keyword=소방` → 실제
  대전광역시 교통신호시설 설치공고(공고번호 R26BK01737901, 오늘 마감) 반환, 나라장터
  상세링크(`bid_ntce_dtl_url`)·첨부파일 다운로드링크까지 자동 포함
- 데이터: 25GB, 투찰자 통합 약 200만 건(2021~2026), 업체정보 10만 건+
- 실서버 배포 인프라 있음(Docker, `app.haehan-ai.kr`) — 상시 가동 여부는 미확인(다음 세션에
  ssh로 확인 필요)

### 1.2 `09. 견적 프로그램(건축,전기,기계,철콘등)`
- 일위대가·품셈(정부 표준 노무/수량 기준)·자재DB·자재단가·공종검색까지 기준서 30개 이상
- "상용화기획안.md" 이미 작성 — 자체적으로 제품화를 준비해온 정황
- 이번 세션에서 API·CLI 진입점까지는 아직 조사 안 함(다음 세션 §6.1)

### 1.3 `03. cad-program`
- 오늘(2026-09-29)도 활발히 작업 중(`.venv`·`.mypy_cache`·`.ruff_cache` 갱신 시각 확인)
- 역할·API 진입점은 이번 세션에서 조사 안 함(다음 세션 §6.1)

### 1.4 `01. haehan-ai-orchestrator` — EUM
- `POST /api/v1/eum/quote/generate`(견적서 자동생성) 포함 API 11개, 실제 임대 22현장 데이터
- CDP 기반(공식 API 없음 — 공공기관 사이트), 매일 자동 점검(`scripts/eum/daily_check.py`,
  단 defect_index #13에 "조용한 실패 의심" 기록 있음 — 다음 세션에 재확인 필요)

## 2. 메일함 연결 (신규 요구사항)

### 2.1 목적
파이프라인의 "사람에게 알림" 지점 — 새 입�찰공고 발견 시(또는 견적·CAD 단계 완료 시)
메일로 통지.

### 2.2 실측: 어느 메일 채널을 쓸 수 있나
| 채널 | 읽기 | 발송 | 실측 상태 |
|---|---|---|---|
| 네이버메일(`naver_mail_router.py`) | 가능 | **고장**(2026-09-29 audit-kit로 발견: `compose`/`send_mail`이 `scripts.naver.mail`에 실제로 없어 dry_run=False 시 100% 크래시) | 이번 세션에서 발견만, 미수정 |
| Gmail(`gmail_router.py`) | 가능 | 구조적으로 정상(CDP로 Gmail 화면의 실제 발송 버튼을 직접 클릭하는 방식, import 깨짐 없음 — 단 라이브 실행 검증은 아직 안 함) | 구조 확인만, 라이브 미검증 |
| Hiworks(`hiworks_mail_router.py`) | 가능 | 라우트는 있음, 이번 세션에서 내부 구현은 확인 안 함 | 미확인 |

`data/naver_mail_inbox_dump.json` 등 실사용 흔적은 네이버메일에 있음(5월 27일). 즉
**읽어온 이력은 네이버메일 쪽이 진짜 쓰던 계정**으로 보이는데, **발송 기능은 그쪽이 고장나
있다**는 모순이 있습니다.

### 2.3 결정 필요
1. 알림 발송을 **어느 메일함**으로 할지(네이버메일 실계정을 쓰고 싶으면 §2.2의 버그부터
   고쳐야 함 — 작은 수정, `scripts.naver.mail`에 실제 발신 로직 연결. Gmail을 쓰면 버그는
   없지만 라이브 검증 필요, 그리고 그게 실제 이 사업 계정인지 확인 필요).
2. 읽기(수신 모니터링, 예: 발주처 문의 메일 자동 분류)까지 연결할지, 발송(알림)만 할지.

## 3. 파이프라인 오케스트레이션 설계 (재사용)

`docs/specs/2026-09-29_ops_automation_buttons_representative_flows.md` §3.1의 흐름을
그대로 재사용한다 — `run_claude_agent` 액션이 Bash로 각 프로젝트의 기존 CLI/API를 직접
호출하는 패턴:

```
[admin-web] "오늘의 신규 공고 확인" 버튼 (또는 예약 실행, §5 참고)
        │ run_claude_agent: "05. g2b api_server.py의 /search를 호출해 신규 공고를 찾고,
        │   09.견적프로그램으로 초안 견적을 내고, 결과를 <메일함>으로 알려줘"
        ▼
[Claude가 Bash로 g2b api_server.py 호출 → 견적 프로그램 CLI 호출(다음 세션 조사 후 확정)
 → 메일 발송 API 호출]
        ▼
[결과를 admin-web에도 표시 + 메일함에도 알림]
```

## 4. 위험

| 위험 | 완화 |
|---|---|
| 4개 프로젝트가 서로 다른 저장소·환경이라 haehan-ai-orchestrator에서 Bash로 부를 때 경로·venv·포트 충돌 가능 | 각 프로젝트를 독립 프로세스로 실행(이미 g2b는 자체 포트 8000), 오케스트레이터는 HTTP 호출만 |
| 네이버메일 발송 버그를 안 고치고 그 계정으로 알림을 보내면 100% 실패 | §2.3 결정 후, 네이버메일 선택 시 버그 수정을 다음 세션 1순위로 |
| g2b의 실서버(`app.haehan-ai.kr`) 상시 가동 여부 불확실 — 로컬로만 돌리면 haehan-ai-orchestrator가 항상 켜져 있어야 함 | 다음 세션에 서버 상태 확인, 필요하면 상시 가동 전환 |
| 4개 프로젝트 각각 방대해서 한 번에 전부 상세 설계 불가 | §6처럼 세션을 나눠 진행 |
