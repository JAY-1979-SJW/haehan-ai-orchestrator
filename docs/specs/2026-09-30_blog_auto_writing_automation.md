**v1/v1.1 이 어긋난 점(정정)**
1. **주제를 임의로 만들었다.** 기준서 §1: "AI가 주제를 지어내지 않는다 — 카페 빈도 + 검색광고 실검색량 + 지식iN 실제 질문 3중 검증 결과만 사용." §6-1 ③ 시험의 주제 3개는 제가 지어낸 것이라 그 통과율은 **참고치**일 뿐이다.

4. **이미 있는 것을 새로 만들려 했다:** 중복 발행 검사(`is_duplicate`·`data/blog_topic_cache.json`, §5.2 에 2026-08-17 이중 발행 사고 이력), SEO 검사(`seo_check`), 이미지(`images.py`), 포스트 간 90초 대기, 주제 리서치.
5. **문서·코드 값 불일치:** 태그 최소 5개(문서) vs 15개(코드), 본문 최소 1,200자(문서) vs 2,500자(코드). 게이트는 코드 값을 쓰고 문서 정정은 별도 과제.
6. **§7 체크리스트 누락:** 발행 로직 변경 시 "라이브 발행 1건 → 실제 페이지 확인 → 나머지" 절차를 D단계에 반영해야 한다.
7. **합치하는 점:** §6 "사용자가 이미 승인한 배치 흐름 안에서는 sub-step 재확인 안 함" = v1 의 "승인한 규칙 안에서 자동 발행" 모델.

## 2. 사용자에게 보이는 기능
1. **규칙 만들기**(블로그 화면의 "자동 작성" 탭): 주제 목록 또는 키워드, 요일·시각, 하루/주 최대 편수, 카테고리, 금칙어, 글 길이, CTA 문구, 이미지 개수, 공개 범위.
2. **승인**: 규칙을 저장하면 "이 범위에서 자동 발행합니다" 요약을 보여주고 사용자가 승인해야 자동 발행이 켜진다. 승인 전에는 **초안 저장까지만**(자동 발행 꺼짐).
3. **실행**: 예약 시각마다 주제 선정 → Claude 작성 → 검사 → 초안 저장 → (통과 + 규칙 범위 안이면) 발행.
4. **관리**: 일시정지/재개, 지금 1회 실행(발행 없는 시험 실행), 실행 이력(성공·건너뜀·중단 이유), 발행 알림.

## 3. 실행 흐름과 안전장치 (자동 발행의 핵심)
```
스케줄 틱 → 규칙 로드 → [사전 조건] → 주제 선정 → Claude(claude -p, 텍스트만) 작성 → 앱이 /compose 저장
   → [품질 검사] → [범위·한도 검사] → 발행(write-to-naver) → 이력·알림
```
| 단계 | 검사 | 실패 시 |
|---|---|---|
| 사전 조건 | 규칙 승인됨 · 일시정지 아님 · **네이버 로그인 상태 `in`**(요소 기준 판정 재사용) · Claude 연동 가능 | 실행 안 함, 이력에 사유, 사용자 알림. **자동 로그인 시도하지 않음** |
| 품질 검사 | 작성 기준서(6단 구성·길이·태그 수) + `seo_check` + 금칙어 + **미검증 수치·경험담 금지**(기준서 §4.1) + 최근 발행글과 주제 중복 | 발행 안 함, **초안으로 남김** + 사유 |
| 범위·한도 | 규칙의 주제 범위·하루/주 한도·허용 시간대·공개 범위 · 규칙 승인 이후 **규칙이 수정되지 않았음**(수정 시 승인 무효) | 발행 안 함, 초안으로 남김 |
| 발행 | 캡차·2단계 인증·모달 등장 시 즉시 중단(입력 시도 금지) | 중단, 초안 보존, 알림 |
- **한도는 코드가 강제**한다(Claude 지시문에 의존하지 않음). 초과분은 무조건 초안.
- **킬스위치**: 일시정지 한 번이면 진행 중 실행 이후 모든 예약이 멈춘다. 연속 실패 3회면 스스로 일시정지.
- 발행 후 수정·삭제는 자동으로 하지 않는다(사용자 수동).
- 프로젝트 규칙(외부 공개 발행은 매번 재확인)에 대한 예외는 **사용자가 규칙을 명시 승인한 범위 안**으로만 한정한다. 승인 기록(누가·언제·규칙 해시)을 남긴다.

## 4. 설계
- **규칙 저장**: 파일 기반 `data/blog_automation/rules/<id>.json` (초안 `data/blog_drafts` 와 같은 방식). DB 스키마 변경 없음. 필드: `id, name, topics[], keywords[], schedule{days,times,tz}, limits{per_day,per_week}, category, forbidden_words[], min_chars, cta, image_count, visibility, mode(draft_only|auto_publish), approval{approved_by,approved_at,rule_hash}, paused`.
- **모듈 배치(레이어)**: 규칙 모델·검사(순수 함수) = L6 `ai_orchestrator/services/blog_automation/` · API = L8 새 라우터 `blog_automation_router.py` · 스케줄러 = 기존 스케줄러 패턴(`gonobi_scheduler` 등)을 **확인해 재사용**(구현 전 확인 항목) · UI = L9 `admin-web` `/naver/blog` 탭. 네이버 발행은 기존 `write-to-naver` 를 **호출만** 한다(재구현 금지, `naver_blog_safety_gate` 유지).
- **Claude 호출 (v1.1 수정)**: **도구 없는 텍스트 생성만 시킨다.** `claude -p --output-format json --max-budget-usd <상한> -- <지시문>` 을 도구 허용 목록·MCP 설정 없이 실행하고, 출력의 `TITLE:` / 본문 / `TAGS:` 를 앱이 파싱한다. 저장(`compose`)·발행(`write-to-naver`)은 **앱이 직접** 호출한다 — Claude 에게 쓰기 도구를 주지 않으므로 오발행 경로가 하나 줄고 권한 관리도 단순해진다. 명령 조립은 기존 `local_agent/actions.py` 의 `claude -p` 조립 방식(예산 상한·모델·`--` 구분자)을 따르되 `--allowedTools` 를 넣지 않는다. 실행 폴더는 저장소 밖 중립 폴더(프로젝트 CLAUDE.md·훅이 딸려 오지 않게). 지시문은 `naver_blog_content_standard.md` 규칙을 조립해 만든다(기준서와 지시문이 어긋나지 않게 한 곳에서 생성).
- **이벤트**: 기존 `emit_event`(NAVER_BLOG_* 계열)에 `NAVER_BLOG_AUTO_RUN` 추가 — 화면 작업 기록 패널이 그대로 보여 줌.

## 5. 단계 (각 단계 끝에서 승인·검증)
| 단계 | 내용 | 발행 여부 |
|---|---|---|
| **A** | 규칙 모델 + 검사 순수 함수(사전조건·품질·한도·승인 무효화) + 테스트. 화면·서버 변경 없음 | 없음 |
| **B** | 규칙 API + 1회 실행기(작성→`compose` 저장까지) + 시험 실행. **실제 발행 코드 연결 안 함** | 없음 |
| **C** | 스케줄러 + 화면(규칙·승인·일시정지·이력) | 초안까지 |
| **D** | 자동 발행 연결 — 승인된 규칙 + 게이트 통과 시에만. 실제 계정에서 1편 시범 발행 후 사용자 확인 | **있음(최종 승인 필요)** |

## 6. 드라이런 계획 (코드 작성 전 확인)
1. 기존 `write-to-naver` 가 dry_run/발행을 어떻게 구분하는지, `seo_check` 의 입력·출력 형태를 코드로 확인.
2. 기존 스케줄러(`gonobi_scheduler`)의 시작 위치·중복 실행 방지·종료 처리 확인 → 재사용 가능 여부 결정.
3. `claude -p` 1회 시험(발행 없음): 샘플 규칙으로 초안을 만들어 **품질 검사 통과율**과 소요 시간·실패 형태 측정.
4. 결과를 이 기준서 §3 검사표의 임계값에 반영.

### 6-1. 드라이런 결과 (2026-09-30, 코드 수정 없음·발행 없음) 와 설계 반영

**① `write-to-naver` / `seo_check`**
| 확인 | 결과 | 설계 반영 |
|---|---|---|
| dry_run 구분 | `publish=False`(기본)면 `save_draft()`, `True`면 `publish()`. 별도 dry_run 플래그는 없음 | B단계는 `publish=False` 만 호출. 발행 호출은 D단계 코드에만 둔다 |
| **자동 로그인이 기본 ON** | `BlogWriter.open(auto_login=True)` — 세션이 무효면 스스로 `ensure_naver_login` 을 시도. 라우트는 이 값을 못 바꿈 | 기준서 §3 "자동 로그인 시도하지 않음"과 충돌. **해결:** ① 실행 전 사전 조건에서 로그인 `in` 을 확인(요소 기준 판정), ② 라우트 요청에 `auto_login: bool = True` 를 **추가만** 하고(기본값 유지 = 기존 호출자 무영향) 자동 실행은 `False` 로 호출 |
| **사용자의 활성 탭을 그대로 사용** | 라우트가 `get_page()` 로 사용자가 쓰던 탭에 글을 씀 | 사용자가 브라우저를 쓰는 중에 탭이 가로채짐. **해결:** 자동 실행은 전용 새 탭(`open_page(allow_new_tab=True, reason=...)`)을 쓰도록 요청 필드 추가 — B단계 착수 전 필수 |
| `seo_check(title, body, keywords) -> {ok, warnings[], ai_ratio}` | 경고만 반환, 차단하지 않음. 검사: 제목 20~60자, 본문 최소 `MIN_BODY_CHARS`, 핵심 키워드 제목·본문 2회, 태그 ≥15, `##` 잔존, `[ ]` 소제목, 내용 없는 표현, 결론 문단, **검증 필요 수치(법령 연도·조항·요율·금액)**, AI 비중 >35% | 자동 발행 기준 = `warnings == []`. `seo_check` 는 그대로 재사용, 금칙어·주제 중복·한도는 앱 쪽 검사로 추가 |
| 문서와 코드 불일치 | 작성 기준서는 본문 최소 1,200자, 코드 `MIN_BODY_CHARS = 2500` | 코드 값(2,500)을 게이트 기준으로 쓰고, 기준서 문구 정정은 별도 과제 |

**② 스케줄러**
- 기존 패턴: `server.py` lifespan 에서 `asyncio.create_task(<x>_schedule_loop())` → 루프 안에서 `await asyncio.sleep(간격)` 후 `asyncio.to_thread(작업)`, 주기마다 `try/except` 로 로그만 남기고 계속, 종료 시 `cancel`(gonobi·community·naver_search 3곳 동일).
- **그대로는 못 쓴다:** 고정 간격 sleep 이고 마지막 실행 기록이 없어 "요일·시각 지정", "하루/주 한도", "재시작 후 중복 방지"를 표현할 수 없다.
- **재사용할 것:** lifespan 태스크 등록·취소, `to_thread` 로 블로킹 작업 분리, 주기별 예외 격리.
- **새로 만들 것:** 1분마다 "지금 실행할 규칙이 있는가"만 판단하는 루프 + 마지막 실행 기록(`data/blog_automation/state.json`). 놓친 회차는 **따라잡지 않는다**(기준서 §8).
- **주의:** `server.py` 는 다른 브랜치(`refactor/server-entrypoint-collision`)에서 `asgi.py` 로 옮겨지는 중 → C단계 등록은 그 병합 뒤에, lifespan 에 **한 줄만** 추가하는 방식으로 충돌을 최소화한다.

**③ `claude -p` 시험 (도구 없음·저장/발행 없음, 주제 3개 동시 실행, 결과는 임시 폴더)**
| 주제 | 소요 | 본문 | 태그 | 기존 `seo_check` |
|---|---|---|---|---|
| 작업일보 엑셀 자동 취합 | 34초 | 2,929자 | 25 | 경고 1건: 핵심 키워드 본문 1회(권장 2회) |
| 준공서류 체크리스트 | 34초 | 2,735자 | 25 | **통과** |
| 카톡 사진 정리 | 39초 | 3,167자 | 25 | **통과** |
- 1회차 통과 2/3. 실패 1건은 키워드 출현 횟수 하나뿐이라 **경고 문구를 지시문에 되먹여 1회 자동 재생성**하면 해결될 가능성이 크다(이 재시도는 아직 시험하지 않음).
- 비용: 편당 약 $0.09(API 환산 값, 사용자 Claude 사용량 한도에서 차감). 발행 수치 경고(`_risky_claims`)는 3편 모두 0건 — 지시문에서 미확인 수치를 금지한 효과로 보이나 3편으로는 단정할 수 없다.
- 직접 읽은 1편은 6단 구성을 지켰고, 불확실한 법령·기한은 "확인이 필요합니다"로 처리했다. **`seo_check` 가 보지 못하는 것**(사실 정확성, 현장 실무 적합성)은 여전히 검사되지 않는다 → 자동 발행 대상 주제를 사용자가 승인한 범위로 좁히고, 초기에는 `draft_only` 로 운영하며 사람이 품질을 보는 기간을 두도록 권장한다.
- 한계: 표본 3편, 한 번의 실행, 주제 3개(건설 실무). 통과율은 추정치다.

**설계 수정 요약 (v1 → v1.1)**
1. Claude 는 텍스트만 생성(도구 없음), 저장·발행은 앱이 직접 호출.
2. 발행 라우트에 `auto_login`, 전용 탭 사용 요청 필드를 **추가만** 한다(기본값 유지).
3. 스케줄러는 lifespan 태스크 패턴만 재사용하고 "지금 실행할 규칙" 판단 루프와 실행 기록을 새로 만든다.
4. 자동 발행 기준은 `seo_check` 무경고 + 앱 검사, 실패 시 1회 재생성 후 초안으로 남김.

## 7. 테스트·검증
- 단위: 한도(하루/주)·시간대·금칙어·중복 주제·승인 후 규칙 수정 시 발행 차단·일시정지·연속 실패 자동정지.
- 변이 시험: 한도 검사 제거, 승인 해시 검사 제거, 로그인 사전조건 제거가 테스트에 잡히는지.
- 실제 화면: D단계 전까지는 **발행 없이** 초안 생성·이력 표시까지. 시범 발행은 D단계 승인 후 1편.

## 8. 위험·한계
- **PC와 Claude가 켜져 있어야 실행됨**(사용자 PC 의존). 꺼져 있으면 그 회차는 건너뛰고 이력에 남김 — 밀린 회차를 몰아서 발행하지 않는다.
- 사용자 Claude 구독의 사용량 한도에 걸릴 수 있음 → 실패로 처리, 재시도는 다음 예약 시각.
- 네이버 화면·정책 변화로 발행이 깨질 수 있음 → 발행 실패는 초안 보존 + 알림, 자동 재시도 없음.
- 저품질·중복 판정 위험은 한도·중복 검사·기준서 §4.1 로 줄일 뿐 없애지 못함.
- 자동 발행은 사용자 계정의 공개 게시물이라 **오발행이 곧 외부 노출**이다 → 기본값은 언제나 `draft_only`, `auto_publish` 는 승인 후에만.

## 9. 되돌리기
새 모듈·라우터·화면 탭 삭제 + `NAVER_BLOG_AUTO_RUN` 이벤트 1개 revert. 기존 발행 API·초안 저장은 수정하지 않는다.

## 10. 승인 요청
**A단계**(규칙 모델 + 검사 순수 함수 + 테스트, 발행·화면·서버 변경 없음)부터 승인 요청. §6 의 드라이런 1~3 은 완료했고 결과는 §6-1 에 있다. **B단계 착수 전에** 발행 라우트에 `auto_login`·전용 탭 필드를 추가하는 변경(§6-1 ①)을 별도로 승인받는다.
