## 결정 (사용자 승인 2026-09-24)
"코드를 수정하거나 신설시 코드맵에 반영해서 드라이런 하는 걸 강제, 코드는 모듈화를 상시하게."
→ 앞서 승인한 3개 설계를 하나로 묶는다:
- 기준서↔코드맵↔골격 3자 대조(docs/specs/2026-09-24_spec_map_skeleton_traceability.md)
- 전체 파일 모듈화·모듈 카드·V0~V6(모듈 설계서 — 이 문서 §3 이 요약)
- 지도↔골격 커밋 게이트(docs/specs/2026-09-24_skeleton_map_crosscheck_gate.md, 구현·검증 중)

## 1. 흐름
| 단계 | 누가 | 무엇 | 강제 |
|---|---|---|---|
| ① 계획 | AI | 기준서 `spec:` 블록에 바꿀 파일·모듈·라우트 | — |
| ② 드라이런 | `impact_plan.py <spec>` | 코드맵 위에 **가상 반영** → 영향 모듈·연결·테스트 수, 예상 층간 위반·순환·골격 불일치, 선언 안 된 연결 | 결과를 `data/impact/<spec-id>.json` 저장 + 사용자에게 표 보고 |
| ③ 승인 | 사용자 | 드라이런 표 보고 승인 | 승인 기록(`approved_at`)이 드라이런 파일에 |
| ④ 시공 | AI | 코드 작성 | — |
| ⑤ 커밋 게이트 | `impact_gate.py`(pre-commit, 목표 3초) | 코드맵 **부분 갱신** + 실제 변경 ↔ 드라이런 계획 대조 + 모듈 소속·선언 안 된 연결 차단 + skeleton_gate | 차단 |
| ⑥ 병합 게이트 | merge_stage → 자체 CI | V0~V6 전체 + 기준서 합격조건 | 차단 |

## 2. 커밋 게이트 규칙 (impact_gate.py)
- 코드 파일 A/M/D/R 이 있는 커밋은 trailer 로 기준서를 가리켜야 함(pre-commit 에서는 메시지가 없으므로 **환경 표시 대신 "현재 진행 기준서" 파일** `data/impact/ACTIVE` 를 읽는다 — 드라이런 시 생성, 병합 후 해제; commit-msg 훅에서 `Spec: <id>` trailer 로 재확인).
- 계획 대조: 실제 바뀐 코드 파일 ⊆ 드라이런 계획 파일(+테스트·정본·문서는 자동 허용). **계획에 없던 코드 파일을 고치면 차단** → 기준서 갱신 후 드라이런 재실행.
- 드라이런이 시공 전 코드 상태(기준 커밋 해시)로 만들어졌는지·승인 기록이 있는지 확인.
- 모듈: 새 파일은 모듈 카드 glob 에 속해야 함(없으면 차단 → 카드 갱신). 모듈 경계를 넘는 새 import 는 카드 `uses` 에 선언돼야 함.
- 사소한 수정: `Spec: trivial` — 코드 파일 1개·순증감 5줄 이하·새 import 없음일 때만 허용(넘으면 거부). 사용 횟수 감사 집계.
- 우회: `IMPACT_GATE_SKIP_REASON`(사유 필수, 메인 저장소 로그).

## 3. 상시 모듈화 — 모듈 카드
- `configs/module_cards/<모듈>.json`: files(glob, **코드+설정+데이터+템플릿+실행파일+문서 전부**), layer, entry(공개 입구: 라우트·MCP 도구·CLI·함수), uses(쓰는 모듈), data(reads/writes), config, docs, checks(V3~V6 검증 정의).
- 모든 추적 파일은 정확히 한 모듈 소속(주인 없음 = 게이트 경고→정리 대상, 신규 파일은 차단).
- 초안은 코드맵 모듈 묶음(modules.py) + 분류 정본에서 자동 생성, 애매한 파일만 사용자 결정.
- 모듈 상태: V0 소속 · V1 구조 · V2 로드 · V3 입구 · V4 계약 · V5 흐름 · V6 실제 사이트.
- **검증 초점 = 연결과 흐름** (사용자 결정 2026-09-24: "원래 되던 것도 검증하는 게 아닌, 연결이 되고 흐름만 보면") — 실측 근거: 오늘 잡은 결함 대부분이 모듈 내부가 아니라 연결 지점(경로·import·재노출·화면→API·입구 소실).
  | 대상 | 병합마다 | 그 외 |
  |---|---|---|
  | 모든 연결(V1 선언·실제 + V4 계약) | **전부** | — |
  | 모든 흐름(V5 드라이런, 외부 부작용 금지) | **전부** | — |
  | 모듈 내부(V2 로드·V3 입구·내부 테스트) | 바뀐 모듈 + 그 연결 이웃만 | 안 바뀐 모듈은 **증거 있는 통과 기록**(마지막 통과 시각·코드 해시) 인정 |
  | 실제 사이트(V6) | — | 매일 |
  | 전체(V0~V6 모든 모듈) | — | **주 1회** 안전망 — 매 병합의 연결·흐름 결과와 어긋나면 검증 설계 구멍으로 보고 보강 |
- 통과 기록이 한 번도 없는 모듈은 첫 회 전체 검증으로 기준선을 만든다.

## 4. 코드맵 부분 갱신 (incremental.py)
- 실측: 전체 build.py 74초(부하 중), modules.py 5초 → 커밋에 전체 빌드는 불가.
- 파일 해시 캐시(`data/code_map/cache/`)로 **바뀐 파일만 재스캔**, 그 파일의 역참조 이웃만 도달성 재계산. 이름 유일성(파일명 문자열 연결 규칙)이 바뀌는 경우(새 파일명이 기존과 겹침)만 관련 엣지 재해석.
- 정확성 담보: 병합 게이트는 항상 전체 빌드. 부분 갱신 결과 = 전체 빌드 결과인지 CI 에서 매번 대조(다르면 부분 갱신 버그로 FAIL).

## 6. 단계 계획
1. 모듈 카드 초안 자동 생성 + 사용자 결정 목록(드라이런) — 소속 애매 파일 수 보고
2. incremental.py + 전체빌드 대조 테스트
3. impact_plan.py(드라이런) — 최근 기준서로 시험
4. impact_gate.py + 훅 연결(install_git_hooks 템플릿) + 깨뜨리기(계획 밖 파일 수정·주인 없는 새 파일·선언 안 된 연결·trivial 남용·드라이런 없음)
5. CI 연결(V0~V6 전체·부분=전체 대조)
6. 공용 스킬 포함(판매 키트 핵심 기능)
