## 3. 핵심 설계: 발송 승인서 (Fax Authorization)
"미리 승인"은 기존 회차 승인과 다른 개념이므로 **별도 승인서**로 만든다. 승인서가 가리킨 정확한 범위 안에서만 자동 발송한다.

- **승인서**가 고정하는 것(= 승인한 범위): ① 수신자 목록(번호·이름) ② 문서(파일 내용 SHA-256 또는 작성 문서 본문 해시) ③ 제목 ④ 한도(1회 최대 건수·1일 최대 건수·총 건수) ⑤ 유효기간 ⑥ 허용 발송 시간대.
- **범위 해시**: 위 ①~③ 의 정규화 해시. 실행 시점마다 현재 값의 해시를 다시 계산해 **승인 때와 한 글자라도 다르면 발송하지 않고 "재승인 필요" 로 멈춘다**.
- 승인은 사람이 앱에서 수신자 목록·제목·문서 미리보기를 본 뒤 명시적으로 한다. 승인자·승인 시각·범위 해시를 기록한다. 승인서는 **취소(즉시 중단)** 할 수 있다.
- 승인서는 예약 작업·이벤트·화면 예약이 공통으로 참조한다 — 자동 발송은 항상 "유효한 승인서 id" 를 요구한다(없으면 발송 거부).

## 4. 안전장치 (외부 수신자에게 나가는 되돌릴 수 없는 발송)
1. **기본은 드라이런**: 승인서에 `live=false` 가 기본. 드라이런은 수신자 검증·중복 검사·한도 계산·발송 계획까지만 하고 실제 전송은 하지 않는다. 실전송은 승인서에 `live=true` 를 명시적으로 켜야 한다.
2. **중복 발송 방지**: 같은 (수신번호, 문서해시) 는 이미 성공 이력이 있으면 건너뛴다(기존 `hanafax_sent_log` + 새 이력 모두 조회). 사용자가 명시적으로 "재발송" 을 선택한 경우에만 허용.
3. **실패 시 자동 재시도 금지**: 전송 요청이 나간 뒤 결과가 불명확하면(타임아웃 등) **재전송하지 않고 "확인 필요"로 멈춘다**(중복 발송 방지가 재시도보다 우선). 명확한 사전 실패(로그인 실패·번호 형식 오류)만 재시도 대상.
4. **한도**: 1회·1일·총 건수 상한, 초과분은 보내지 않고 남긴다. 한도는 승인서에 고정.
5. **킬 스위치**: 전역 정지 플래그(앱에서 한 번에 모든 자동 발송 중단) + 승인서별 취소. 정지 상태에서는 어떤 경로로도 발송하지 않는다.
6. **잔액 확인**: 발송 전 잔액이 필요한 건수보다 적으면 발송하지 않는다(과금·결제는 사용자 영역 — 충전은 자동화하지 않는다).
7. **허용 시간대**: 승인서의 시간대 밖에서는 발송하지 않는다(심야 발송 방지).
8. **감사 기록**: 모든 판정(발송·건너뜀·거부·사유)과 접수번호를 기록한다. 수신번호는 마스킹해 로그에 남기고 전체 번호는 승인서·이력 DB 에만 둔다. 자격증명·문서 본문은 로그에 남기지 않는다.
9. **수신자 목록 안전성**: 번호 형식 검증, 목록 내 중복 제거, 수신거부 목록(opt-out) 제외(영업공문 대량 발송의 법적·평판 위험 — 수신거부 번호는 영구 제외).
10. **테스트는 실제 발송을 하지 않는다**: 단위·통합 테스트는 가짜 발송기로만. 실전송 검증은 사용자 승인 하에 **본인 번호 1건**으로만(과금 최종 확인은 사용자).

## 6. 네 가지 발송 내용의 연결
- **정기 발송**: 예약 작업의 반복 규칙(recurrence)이 이미 있다 → 승인서 id 를 가진 `hanafax_send` 작업.
- **화면 예약 발송**: 화면에서 수신자·제목·문서를 입력 → 미리보기 → 승인서 생성·승인 → 지정 시각에 예약 작업 실행.
- **영업공문 대량**: 엑셀+배치 JSON 을 승인서의 수신자 목록으로 가져온다(배치 파일 위치는 `HAEHAN_FAX_EXPORT_DIR`/형제 프로젝트 `05. g2b` — 이번에 하드코딩 해소). 건수가 크므로 1회·1일 한도로 나눠 발송.
- **이벤트 발송(입찰·공고 알림)**: **트리거 인터페이스만 만든다**(`이벤트 → 승인서 id + 변수(공고명 등)`). 승인서의 문서가 템플릿이면 변수를 채운 결과를 해시로 승인할 수 없으므로, 이벤트 발송은 **"템플릿 + 허용 변수 목록" 을 승인 범위로** 하고 변수 값은 길이·문자 검증만 한다. 실제 이벤트 원천(나라장터 공고 수집 등)은 **사이트 연결이라 보류** — 사용자가 해당 사이트를 지목할 때 붙인다.

## 8. 위험·대응
- **오발송**: 범위 해시 불일치 시 정지, 드라이런 기본, 승인 전 미리보기, 킬 스위치.
- **중복 발송**: 성공 이력 조회 + 불명확 결과는 재시도 금지.
- **사이트 변경으로 자동화 깨짐**: 하나팩스는 공개 API 가 없어 화면 의존. 발송 직전 사전 점검(로그인·잔액)을 하고, 결과를 확정 못 하면 "확인 필요" 로 멈춘다.
- **다른 세션과의 충돌**: `scheduled_job_actions.py`·`router.py`·`nav.ts` 는 메일 세션이 수정하는 파일 — 착수 전 겹침 확인, 커밋은 파일 지정.

### 9.3 구현 계획
1. **즉시 발송**: 승인서(사전 승인)로 자동 발송하는 P1·P2 완료. 남은 것 — 실제 발송기 어댑터(`send_fax` 호출, `definite_failure` 구분), 승인서 API, 승인 화면.
2. **예약 발송**: 두 가지 방법 중 선택 필요 — (a) 앱 예약 작업 프레임워크의 시각에 발송(앱이 켜져 있어야 함, 이미 구현됨), (b) 하나팩스 사이트의 자체 예약 기능(`pop_ReserveSel.asp`)에 예약 등록(앱이 꺼져도 발송됨, 사이트 화면 실사 필요). (a) 로 먼저 하고 (b) 는 실사 후 판단.
3. **그룹 발송**: 하나팩스 주소록(`address_List.asp`)을 앱의 수신자 그룹으로 가져오거나 앱 자체 그룹을 승인서의 수신자 목록으로 쓴다 — 주소록 화면 실사 필요.
4. **실사(읽기 전용)**: 하나팩스에 로그인된 브라우저가 필요하다. **로그인은 사용자만 가능**(프로젝트 규칙). CDP 브라우저를 켜고 사용자가 한 번 로그인하면 이후 화면 탐색은 AI 가 읽기 전용으로 수행한다.

## 10. 화면·AI 창 연동 (P4, 2026-10-02 사용자 지시)
지시: "앱에 하나팩스 탭을 별도 페이지로 만들고 AI 창과 연동, 첨부 파일 경로를 알려주면 알아서 첨부해 발송하되 **발송 전 승인 요청은 필수**", "**발송 전 미리보기 목차는 보여 주되 볼지 말지는 사용자 몫**".
- **탭**: `/hanafax`(nav 항목 "하나팩스"). 왼쪽 = 요청 목록·상세·승인·지금 발송·이력·전체 정지, 오른쪽 = AI 창(`UniversalChat`). 승인 대기 건은 4초마다 새로 고쳐 AI 창에서 올린 요청이 바로 보인다.
- **AI 연동**: AI 에이전트(MCP `call_api` 허용목록)는 `hanafax.draft`(승인 대기 초안 생성 — 전송 없음)·`hanafax.authorizations`(조회)만 쓸 수 있다. 첨부 파일 경로·수신자·제목을 받아 초안을 만들고 "하나팩스 탭에서 승인하세요"라고 안내한다. **승인·발송·정지·수신거부·취소는 허용목록에 없다**(테스트가 고정).
- **승인 필수**: 서버가 승인 전 `run` 을 거부(`not approved`). 승인은 화면의 "이 내용으로 승인" 버튼(`confirmed=true`)으로만. 승인 시 문서 내용이 요청 때와 같은지 재확인하고, 발송 직전에도 해시를 다시 비교한다.
- **미리보기 = 선택 사항**: 상세의 "미리보기 보기(선택)" 를 펼치면 ① 제목 ② 첨부 파일 경로 ③ 수신자 목록 ④ 한도 ⑤ 발송 시간대 목차가 보인다. 펼치지 않아도 승인·발송할 수 있다(보기를 강제하지 않는다 — 승인 행위 자체는 필수).
- **기본 드라이런**: "실제로 전송" 을 체크해야 실전송 승인이 된다.
- **남은 위험**: 로컬은 `AUTH_ENABLED=False` 일 수 있어 API 인증이 약하다. AI 가 승인 API 를 직접 부르는 것은 MCP 허용목록과 `--allowedTools`(MCP 도구만)로 막고 있으나, 별도 셸 도구가 열린 세션이면 이론상 가능 — 승인 버튼에 사람 확인 토큰(예: 일회용 코드)을 두는 강화는 P5 전에 검토.
- 다음: P5 본인 번호 1건 실전송(사용자 승인·과금 확인), 예약 발송 화면 연결.

## 11. AI 창 승인 카드·주소록 대량·단체발송 (P4b, 2026-10-02 사용자 지시)
- **사용자 흐름**: AI 창에 문서 경로 + 전화번호(또는 주소록 엑셀/CSV 경로)를 준다 → AI 가 `hanafax.draft` 로 승인 대기 초안을 만들고 답변 끝에 `[[fax-approve:<id>]]` 를 적는다 → **AI 창 안에 승인 카드(버튼)가 나타난다** → 사용자가 "승인하고 발송"을 누르면 끝까지 자동 발송. 승인은 사람이 버튼으로만 하고, AI 는 승인·발송 API 를 쓸 수 없다(허용목록 테스트 고정). 미리보기는 카드 안 접이식(선택).
- **주소록 가져오기**: `recipients_file`(xlsx/csv). '팩스' 열(없으면 '연락처'·'전화')과 '업체명' 열을 자동 인식. 잘못된 번호·중복·수신거부·**예전 발송 이력(`data/hanafax_sent_log.json`)에서 이미 성공한 번호**는 빼고 건수를 `import_summary` 로 알린다. 한도는 비우면 수신자 수만큼(상한 1000).
- **단체발송**: 수신자가 2명 이상이면 하나팩스 단체발송(`send_fax_bulk`, 로그인·업로드 1회)으로 50곳씩 묶어 보낸다. 묶음마다 정지·취소를 다시 확인하고, 묶음 결과가 불명확하면 남은 묶음을 보내지 않고 멈춘다(재전송 금지). 1명이면 기존 단건 경로.
- **테스트 안전**: 가짜 발송기가 단건·단체발송 두 엔진 경로를 모두 막는다(실제 사이트에 닿지 않는다).

## 12. 하나팩스 실제 화면 미리보기 (방식 A, 2026-10-02 사용자 승인)
- **동작**: 승인서의 수신번호·제목·첨부를 하나팩스 국내팩스 접수 화면에 실제로 채우고(로그인 → 번호 추가 → 제목 → 첨부 변환 대기) **전송하지 않고 스크린샷만** 찍는다. 승인하면 같은 절차로 다시 열어 실제 전송한다(미리보기와 전송은 서로 다른 세션).
- **전송 불가 보장**: `scripts/hanafax/preview.py` 에는 "팩스보내기" 버튼 셀렉터가 없고(테스트 고정), 결과 페이지(`submit_Result`) 이동을 브라우저에서 차단하며, 사이트 대화상자는 전부 취소한다. 엔진(`sender.py`)은 수정하지 않았다. 엔진과 같은 락을 써 발송과 동시에 돌지 않는다.
- **API**: `POST /hanafax/authorizations/{id}/preview`(백그라운드 시작) · `GET …/preview`(상태) · `GET …/preview.png`(이미지). AI 허용목록에는 없다(사람이 화면에서만).
- **화면**: AI 창 승인 카드와 하나팩스 탭 상세에 "하나팩스 실제 화면으로 보기 (선택)". 눌러야 만들며(30~60초) 보지 않아도 승인할 수 있다. 수신 30곳 초과면 처음 30곳만 채우고 안내한다.
- **보관**: 스크린샷에 수신번호·계정명·잔액이 보이므로 `data/hanafax_preview/` 로컬에만 둔다(`.gitignore` 의 `data/**/*.png` 로 커밋 제외).
- **실측(2026-10-02)**: 없는 번호 3곳으로 앱에서 만들어 확인 — 받는 사람 3명·제목·변환된 첨부(.tif)·바로전송·전송 내역 3명이 사이트 화면 그대로 표시되고 전송은 일어나지 않았다.

### 13.1 후속 (같은 날)
- **"확인 필요" 해소**: 하나팩스 탭 상세에 결과를 확정하지 못해 멈춘 번호가 표시된다. 사람이 하나팩스 "전송결과"에서 확인한 뒤 **"발송됨 확인"**(성공 기록, 다시 보내지 않음) 또는 **"발송 안 됨(재전송 허용)"**(실패 기록, 다시 보낼 수 있음)을 PIN 으로 처리한다. `POST /hanafax/authorizations/{id}/resolve`. AI 허용목록에는 없다.
- **한도 집계 보정**: `count_sent` 를 번호별 **가장 최근 상태** 기준으로 바꿨다 — 해소된 '발송 안 됨' 번호는 한도에서 빠지고, '발송됨'으로 해소된 번호가 불명+성공으로 두 번 세어지지 않는다(선점만 남은 번호는 보수적으로 포함).
- **초안 만료**: 승인 대기 초안은 만든 지 24시간이 지나면 승인할 수 없다(`draft_expired`). 승인 카드에 요청 시각·요청자를 표시한다(오래된 초안으로 카드를 다시 띄워 승인을 유도하는 것 방지). 승인된 건은 만료 대상이 아니다.

### 13.2 예약 작업 화면 확인·보완 (같은 날, 앱에서 실측)
- **확인**: 예약 작업 화면에서 "하나팩스 자동 발송" 선택 → 승인서 선택 → 저장 → "지금 실행" 이 끝까지 동작(드라이런 승인서: `dry_run` 이력만 남고 전송 없음).
- **보완**: ① 승인서 선택 항목에 `이름 · N곳 · 승인 날짜 · 드라이런/⚠ 실전송` 표시(이름이 같아도 구분), ② 예약 목록 행에 승인서 이름 표시(취소돼 사라졌으면 "실행되지 않습니다" 경고), ③ 실전송 승인서를 고르면 "예약 시각에 사람 확인 없이 발송" 경고 표시, ④ 하단 안내에 "하나팩스는 예약 시각마다 승인하지 않고 승인서를 PIN 으로 승인할 때 한 번만 승인" 명시, ⑤ 승인서 선택 기본값을 화면의 첫 항목과 일치(선택을 건드리지 않고 저장해도 빈 값이 가지 않도록).

## 15. 전송결과 대조 — 최종 성공/실패 확정 (2026-10-02, 실사 §14 후속)
- **문제**: 사이트의 "팩스 전송 완료"는 *접수* 문구다. 앱의 `sent` 는 접수일 뿐이고, 번호가 없거나 수신 불가면 전송결과에서 나중에 "전송 실패"가 된다(없는 번호 테스트 4건이 모두 그랬다).
- **상태 추가**: `delivered`(전송결과에서 최종 성공 확인), `delivery_failed`(최종 실패 확인). 한도 집계는 둘 다 포함하고, `delivery_failed` 번호는 **사람이 해소하기 전까지 자동 재전송하지 않는다**(`확인 필요` 목록에 나타나 PIN 으로 "발송됨/발송 안 됨" 처리). 중복 방지(`sent_numbers`)·집계는 번호별 **가장 최근 상태** 기준이라 해소·재전송 이후 상태가 반영된다.
- **읽기**: `scripts/hanafax/send_result.py` — 전송결과 화면 표만 읽는다(삭제·예약취소·저장 버튼 안 누름, 엔진과 같은 락). 셀 내용 패턴(보관기한·건수·상태·전송일)으로 해석한다. 데이터 행이 안쪽에 표를 품고 있어 **직계 셀에 보관기한이 있는 행**을 읽는다(실측으로 확인·수정).
- **대조**: `services/hanafax_reconcile.py` — 보수적 매칭(제목 일치[사이트가 줄인 `..` 접두 허용] · 앱 기록 시각과 사이트 전송 시각 10분 이내 · 같은 전송으로 묶인 번호 수 = 사이트 '전체' · 한 건이면 번호도 일치). 하나라도 안 맞으면 **아무것도 바꾸지 않고** `unmatched`. 일부만 성공(혼합)이면 건별 판정 불가라 `partial` 로 두고 상세 확인을 안내한다.
- **실행**: 하나팩스 탭의 "전송결과 확인(최종 성공/실패)" 버튼, 그리고 **발송이 끝나고 3분 뒤 자동**(백그라운드, 실패해도 발송·이력 불변). API `POST/GET /hanafax/authorizations/{id}/reconcile`(AI 허용목록에 없음).
- **실측**: 앱이 `sent` 로 기록한 단체발송 3건이 사이트의 "전송 실패 3/3" 과 매칭돼 `delivery_failed` 3건으로 확정됐다(처음 시도는 표 행 선택 오류로 0건 → 안전하게 `unmatched`, 수정 후 정상).
- **한계**: 혼합 결과(일부 성공)는 상세 화면을 열어야 건별 확정 가능(미구현), 오늘 이전 행은 분 단위 시각이 없어 대조하지 않는다(발송 직후 대조가 전제), 한 번호가 여러 전송에 걸친 경우는 묶음 단위로만 판정.

## 16. 하나팩스 주소록 그룹 가져오기 (2026-10-02, 실사 §14 후속)
- **읽기 전용**: 주소록 메뉴를 눌러 그룹(`address_pList.asp?intid=…`)을 열고 10명씩 `goPage(n)`(쪽 이동 요소는 `<button onclick="goPage(n)">`)으로 넘겨 읽는다(`scripts/hanafax/address_book.py`). 추가·변경·삭제·보내기는 누르지 않는다. 직접 URL 이동은 홈으로 돌아가므로 메뉴를 눌러 들어간다.
- **2단계**: ① 그룹을 백그라운드로 읽어 **로컬 캐시**(`ai_orchestrator/storage/fax_address_cache/<intid>.json`, `storage/` 커밋 제외, 24시간 유효)에 저장(큰 그룹은 100쪽 넘어 몇 분 — 쪽 진행률 표시) ② 승인서 생성에 `site_group`(그룹 번호)+`group_offset`/`group_limit` 로 구간을 지정해 수신자를 만든다(1000명 상한이라 큰 그룹은 1000명씩 나눠 승인). 캐시가 없거나 24시간이 지났으면 거부하고 다시 가져오라고 안내한다.
- **검수 공용화**: 엑셀 주소록과 같은 `_screen` — 잘못된 번호·중복·수신거부·예전 이력에서 이미 보낸 번호는 빼고 건수를 `import_summary` 로 알린다(구간 정보 `group_total`·`range_start`·`range_end` 포함).
- **화면**: 새 발송 요청 폼의 "하나팩스 주소록 그룹" 모드 — 그룹 불러오기 → 선택(이름·인원) → "이 그룹 가져오기" → 구간 지정 → 승인 대기로 올리기.
- **AI**: 허용목록에 읽기 전용 3개 추가(`hanafax.address_groups`·`address_group_sync`·`address_group_sync_status`)와 `hanafax.draft` 의 `site_group`. AI 는 그룹 목록 확인 → 가져오기 → 진행 확인 → 초안 생성까지만 하고, 승인·발송은 여전히 사람이 PIN 으로 한다.
- **실측(앱에서)**: 4개 그룹(최대 1129명) 목록을 읽고, 11명 그룹을 가져와(2쪽) 11곳 승인 대기 초안을 만들었다(화면 흐름·AI 창 흐름 모두). 51명 그룹은 6쪽, 중복 없이 51명. 1129명 그룹 전체(113쪽)는 시간 때문에 가져오기를 실행하지 않았다.
- **개인정보**: 캐시·스크린샷에 연락처가 있으므로 로컬에만 둔다. 모듈은 아무것도 저장하지 않는다(호출자가 캐시에만 기록). 테스트용 캐시는 삭제했다.
- **한계**: 1000명이 넘는 그룹은 구간을 나눠 각각 승인해야 한다. 사이트에서 그룹이 바뀌면 캐시가 낡을 수 있어 24시간 TTL 로 제한한다.

## 17. 실패해도 과금되는가 — 사이트 이용내역 조회 결과 (2026-10-02, 읽기 전용)
**결론: 전송 실패 건은 과금되지 않았다.** (이번 테스트 4건: 없는 번호 5곳 접수 → 전송결과 모두 "전송 실패")
- **이용내역**(`Account/acc_faxsubmit.asp`)은 **"이용(성공) 건수"와 요금만 집계**한다(상세내역도 성공 건만 나열, 성공 1건 = 124원). 기간 "오늘" 조회: **팩스 0건 · 0원**. 최근 1개월 합계는 9월 8일까지의 성공 발송 분뿐이고 10월 2일의 실패 테스트는 한 줄도 없다.
- **결제내역**(`Account/acc_accountPage.asp`)에는 이번 실패 건과 관련된 항목이 없다(월 이용료·충전 결제만 있음).
- **정정**: §14 에 적었던 "잔액이 300원 줄었다"는 관측은 **오독**이었다 — 당시 미리보기 이미지의 잔액을 확대해 보니 지금 잔액과 같다(7과 4를 혼동). 잔액 변동은 없다. (교훈: 화면 이미지의 숫자는 눈으로 읽지 말고 텍스트(DOM)로 읽는다 — 앱의 미리보기·대조는 DOM 텍스트를 쓴다.)
- **주의(과금 조건)**: 전송결과 화면 안내문 — 수신 시 *사람·자동응답기가 받으면 발송완료로 처리되어 과금*. 즉 "번호가 맞아 응답기가 받은 건"은 성공(과금)이고, 없는 번호처럼 연결되지 않아 "전송 실패"가 된 건은 과금되지 않는다. 다만 실패 처리 기준(통화 중·무응답 재시도 정책)은 사이트 정책이라 앱이 보장하지 않는다 — 대량 발송 후에는 이용내역·전송결과로 사후 확인한다.
- **의미**: 단체발송의 실패 번호가 비용을 만들지 않으므로 "접수(sent) 후 delivery_failed" 가 늘어도 비용 위험은 낮다. 비용은 **성공 건수 × 단가**(전송결과 대조의 `delivered` 건수로 사전 추정 가능).

## 18. 큰 그룹 실측 · 혼합 결과 세부 대조 (2026-10-02)
**큰 그룹(§16) 실측**: 1129명 그룹을 앱의 가져오기로 읽었다 — 113쪽, 약 2분, 인원이 사이트 표기와 일치. 번호 기준 고유 1079명(그룹 안에 같은 번호 50건 중복), 이름 없는 항목 0. 1000명 구간(수신 947명: 중복 39·이미 보낸 번호/수신거부 14 제외)과 나머지 구간(수신 128명)으로 나뉘어 승인 대기 초안이 만들어졌고, 범위를 벗어난 구간은 거부됐다(테스트 초안·캐시는 정리).
- 주의: 구간 사이에 같은 번호가 걸쳐 있어도 중복 방지는 실행 시점에 문서 해시로 걸러진다(같은 문서를 두 번 보내지 않는다).

**전송결과 세부내역(읽기)** — 건 하나의 번호별 최종 결과:
- 목록의 제목 링크는 `javascript:detail(건ID, 0)`(홍보 레이어에 가려져 클릭이 막힐 수 있어 **함수를 직접 호출**한다 — "다시 보지 않기" 같은 사이트 설정 변경 버튼은 누르지 않는다).
- 세부 화면 = 기본정보(관리제목·**수신번호 전체**·전송일시·전송상태·완료일시) + 사유별 인원 표(완료 / 일부 페이지 전송 완료 / 사람·자동응답기 받음 → **발송완료(과금)**, 통화 중 / 잘못된 전화번호 / 응답 없음 / 상대방 수신거부 / 회선불량 / 기타 → **발송 미완료**). 인원 숫자 링크 `get_submitList(건ID, 구분)` → 팝업 `pop_sendDetail.asp`(이름·수신팩스번호·전송완료시간).
- 실측: 없는 번호 3곳 전송 → 전원 "응답 없음", **접수 9분 뒤에 완료**(사이트가 몇 분간 재시도 후 확정) → 자동 대조를 발송 3분·15분 뒤 두 번 한다. "다시 전송하기" 등 동작 버튼은 누르지 않는다.
- **대조 반영**: 일부만 성공한 혼합 결과는 세부내역의 번호별 결과로 건별 확정(`delivered`/`delivery_failed`, 사유를 이력 메시지에 남김). 조건: 건 ID 존재 · 세부내역의 번호 집합 = 앱의 접수 묶음과 정확히 일치 · 모든 번호의 결과 확인. 하나라도 어긋나거나 읽기에 실패하면 아무것도 바꾸지 않고 `partial` 로 남긴다.
- 한계: 혼합 결과 경로는 실제 데이터가 없어(테스트 발송은 모두 전원 실패) 주입 테스트로만 검증했다 — 실제 혼합 건이 생기면 첫 대조 결과를 확인할 것. 전원 성공/실패 경로는 실측 완료.
