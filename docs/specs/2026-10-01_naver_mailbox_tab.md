# 네이버 메일함 정식 탭 — 기준서 (초안, 승인 대기)

- 날짜: 2026-10-01 / 사용자 요청: "메일함의 정식 탭을 만들어서 목차(폴더 목록)도 나오게 하고, 네이버 메일 페이지처럼 첨부 파일 기능까지 똑같이 구현"
- 전제: 수신·발송 프로토콜 계층은 이미 있다(`scripts/naver/mail_imap/` reader·sender, 절차서 `2026-10-01_naver_mail_imap_smtp.md`). 이 문서는 그 위에 **앱 화면(탭)** 을 얹는다.
- 기존 "메일 비서"(`/mail`)는 Gmail 전용이므로 건드리지 않고, 네이버용 **"메일함"(`/mailbox`)** 을 새 탭으로 둔다.

## 1. 화면 구성 (네이버 메일 웹과 같은 3단)
```
┌ 목차(폴더) ┐┌ 메일 목록 ──────────────┐┌ 읽기 창 ─────────────────┐
│ ✉ 메일쓰기 ││ [검색…] [전체|안읽음|첨부]││ 제목 / 보낸 사람 / 날짜     │
│ 받은편지함 76││ ☐ 보낸이  제목 📎  날짜  ││ 📎 첨부 2개 [다운로드][미리보기]│
│ 보낸메일함  ││ ☐ …                    ││ 본문(HTML, 격리 표시)        │
│ 임시보관함  ││ 페이지 ◀ 1 2 3 ▶       ││ [답장][전체답장][전달][삭제]  │
│ 휴지통/스팸 ││                        ││                           │
│ 내 폴더…   ││                        ││                           │
└───────────┘└────────────────────────┘└──────────────────────────┘
```
- **목차**: IMAP 폴더 목록(+ 안 읽은 수). 실계정에서 **"내게쓴메일함"도 IMAP 폴더로 보인다**(자기에게 보낸 메일은 거기에 들어간다 — 받은편지함이 아니다). 네이버 시스템 폴더(받은편지함·보낸메일함·임시보관함·휴지통·스팸)는 한글 이름으로 고정 순서, 사용자 폴더는 그 아래(UTF-7 이름을 한글로 변환). 하위 폴더는 들여쓰기.
- **목록**: 한 페이지 30통, 최신순, 안 읽음 굵게, 첨부 클립 아이콘, 크기, 날짜. 필터(전체/안읽음/첨부), 검색(제목·보낸 사람·기간).
- **읽기**: 헤더(보낸 사람·받는 사람·참조·날짜), 첨부 목록, 본문.
- **쓰기**: 받는 사람/참조/숨은참조, 제목, 본문, **파일 첨부**(선택·끌어놓기), 보내기.

## 2. 첨부 파일 (이번 요청의 핵심)
| 기능 | 방식 | 안전장치 |
|---|---|---|
| 첨부 목록 | 목록의 클립 아이콘은 서버 `BODYSTRUCTURE` 의 disposition=attachment 로 판단(multipart 여부만 보면 인라인 이미지뿐인 메일에도 붙는 오탐이 있어 교체, 2026-10-01 실계정 확인). 상세에서는 파일명·크기·형식을 보여 줌 | 파일명은 MIME 디코딩 후 경로 문자 제거 |
| 다운로드 | 해당 첨부 파트만 IMAP 에서 받아 **스트리밍 응답**(디스크에 안 남김) | 1개 25MB 상한, `Content-Disposition: attachment` + `X-Content-Type-Options: nosniff` |
| 미리보기 | 이미지·PDF·텍스트만 읽기 창 안에서 표시 | 그 외 형식은 다운로드만. HTML 첨부는 미리보기 금지 |
| 보낼 때 첨부 | 화면에서 업로드 → 메모리에서 MIME 조립 → SMTP | 파일당 20MB·합계 25MB(네이버 한도 확인 후 조정), 실행 파일(exe·bat·scr 등) 거부, 파일명 정리 |
| 인라인 이미지 | 본문 속 `cid:` 이미지는 해당 파트로 연결해 표시 | 외부 이미지는 기본 차단 + "이미지 표시" 버튼 |

## 3. 읽음 표시·삭제 규칙
- **사용자 결정(2026-10-01): 메일을 열어도 읽음 처리하지 않는다**(`BODY.PEEK`). 읽음 표시는 읽기 창의 **"읽음으로 표시/안 읽음으로 표시" 버튼**으로만 바꾼다. 분석용 조회(`reader.py`)도 읽음 표시를 바꾸지 않는다.
- 삭제는 **휴지통으로 이동**만(영구 삭제는 휴지통 비우기를 사용자가 직접 눌렀을 때만). 확인 창을 거친다.
- 폴더 만들기·이동·스팸 신고는 2차.

## 4. 보내기 승인 (프로젝트 규칙: 메시지 전송은 매번 확인)
- 쓰기 창의 **"보내기" 버튼이 사용자의 승인**이다: 누르면 받는 사람·제목·첨부 목록을 보여 주는 확인 창이 한 번 더 뜨고, 거기서 "전송"을 눌러야 나간다.
- 서버 API 는 관리자 로그인 필요 + 요청마다 확인 토큰(확인 창에서 발급)을 요구한다. **AI 가 이 API 를 임의로 호출해 보내지 못하게** 하기 위한 장치다(AI 경유 발송은 기존 예약 작업 `naver_mail_send` 의 회차 승인만 쓴다).
- 받는 사람 최대 20명(참조·숨은참조 포함), 제목 한 줄, 본문 20,000자.

## 5. 보안
- 본문 HTML 은 **샌드박스 iframe(`sandbox` 속성, 스크립트 금지) + CSP(외부 리소스 차단)** 로만 표시. 앱 DOM 에 직접 삽입하지 않는다.
- 앱 비밀번호는 서버에서만 사용, 응답·로그에 노출 없음. 계정은 `.env` 에 앱 비밀번호가 있는 네이버 계정만 선택 가능.
- 연결은 요청마다 새로 열고 닫는다(IMAP 장기 연결 유지 안 함). 로그인 실패는 1회 후 중단(계정 잠금 방지, 기존 규칙 유지).
- 첨부 다운로드·업로드 크기 상한과 형식 제한은 서버에서 강제(화면 검사는 보조).

## 10. 추가 요구 (2026-10-02 사용자 지적 4건) — 1차 화면 보완

| 지적 | 원인 | 조치 |
|---|---|---|
| 외부 참조 이미지가 차단됨 | 기준서 5절의 "외부 이미지 기본 차단" 설계대로 동작했으나 네이버 웹은 기본 표시 | **기본 표시**로 바꾸고 읽기 창에 "이미지 차단/표시" 토글을 둔다(선택은 이 브라우저에 기억). 본문은 여전히 스크립트 금지 iframe + CSP(`img-src https: http: data:` 만 열고 script·frame·connect 는 막음) |
| 삭제가 느림 | 서버 삭제는 약 1초(로그인 0.4s + 폴더 조회 + MOVE). 화면이 삭제 뒤 목록 재조회 + 목차 재조회(폴더 14개 STATUS ≈ 1.4s)를 **끝까지 기다린 뒤** 갱신 | 화면에서 **즉시 행을 지우고 안 읽은 수를 로컬로 갱신**(낙관적 갱신), 재조회는 백그라운드. 서버는 휴지통 폴더 이름을 계정별로 기억해 `LIST` 생략, 여러 통은 연결 1번으로 일괄 처리 |
| 목차/목록에 삭제·이동 버튼 없음 | 1차 범위를 읽기 창 단건 삭제만으로 잡았고 이동·일괄 선택은 2차로 미뤘음 | 목록에 **체크박스 + 도구줄**(삭제 · 이동 ▾ · 읽음 · 안 읽음 · 스팸 이동), 휴지통/스팸 폴더에서는 **영구 삭제**와 **비우기**(확인 창 필수, 이 두 폴더에서만 허용), 읽기 창에도 이동 버튼 |
| 메일 쓰기에 네이버 같은 편집기 없음 | 1차 쓰기 창 본문을 일반 텍스트로만 설계함 | **서식 편집기(WYSIWYG)**: 글꼴 크기·굵게·기울임·밑줄·취소선·글자색·배경색·정렬·목록·인용·링크·구분선·이미지 삽입·서식 지우기·실행 취소. HTML + 텍스트 대체본(multipart/alternative) 로 발송, 삽입 이미지는 본문 속 첨부(cid)로 전송 |

### 10-1. 편집기·HTML 안전 규칙
- 서버가 보낼 HTML 을 **허용 목록 방식으로 정제**(`scripts/naver/mail_imap/html_sanitize.py`, 표준 라이브러리): 허용 태그·속성·CSS 속성만 남기고 `script/style/iframe/form/on*` 은 제거, 링크는 `http/https/mailto` 만, 이미지는 `data:image/(png|jpeg|gif|webp)` 와 `cid:` 만(외부 이미지 주소는 추적 위험으로 제거).
- 답장/전달의 원문 인용도 **서버가 정제한 `quote_html`** 만 편집기에 넣는다(받은 HTML 원문을 앱 화면 DOM 에 넣지 않는다 — 앱 출처에서 스크립트가 실행되는 것을 막기 위함).
- 텍스트 대체본은 정제된 HTML 에서 서버가 만든다. 화면의 "보내기 → 전송 확인 창"은 그대로(정제된 본문 미리보기 표시).

### 10-2. 일괄 처리 API (추가)
`POST /naver-mailbox/move {account, folder, uids[], dest}` · `/trash {…, uids[]}`(단건 `uid` 도 허용) · `/flags {…, uids[], seen}` · `/purge {…, uids[]}`(휴지통·스팸에서만) · `/empty {account, folder}`(휴지통·스팸에서만). 한 번에 최대 100통.

## 11. 클릭 반응속도 개선 — 원인·조치·앱 창 실측 (2026-10-02)

### 11-1. 원인 (앱 창에서 측정)
- 요청마다 IMAP 연결(TLS)+로그인을 새로 함 → 메일 하나 열 때마다 약 0.4초가 로그인.
- 헤더·본문을 읽는 서버 요청은 100통당 약 4.4초(메일 내용을 읽는 모든 FETCH 가 비슷), 플래그·크기만 읽는 요청은 0.03초.
- 화면: 새 메일을 받는 동안 이전 메일이 그대로 남아 클릭이 먹통처럼 보임, 같은 메일을 다시 열어도 서버를 다시 거침.

### 11-2. 조치
| 위치 | 조치 |
|---|---|
| 서버 `mailbox.py` | **IMAP 연결 풀**: 계정당 인증된 연결 최대 3개를 45초간 보관·재사용(꺼낼 때 NOOP 확인, 죽은 연결은 교체, 작업 중 오류가 난 연결은 풀에 돌려놓지 않고 닫음). 테스트처럼 factory 를 직접 주면 풀을 쓰지 않음 |
| 서버 | **헤더 캐시**(UID+크기 키, 읽음 상태만 매번 새로 받음), **메일 원문 캐시**(60통·40MB 상한 — 다시 열기·첨부 받기에 재사용), **다음 페이지 미리 데우기**(백그라운드 스레드) |
| 화면 | 클릭 즉시 목록 정보로 제목·보낸 사람·날짜를 표시하고 본문은 이어서, **마우스를 120ms 올려 두면 메일을 미리 받음**, 한 번 연 메일은 화면에도 캐시(읽음 표시는 목록의 최신 값을 따름), 목차에서 폴더에 마우스를 올리면 첫 페이지를 미리 받아 둠(1분에 한 번) |

### 11-3. 앱 창 실측 (Haehan AI 앱 webview, 프록시 경유)
| 동작 | 개선 전 | 개선 후 |

### 11-4. 남은 한계
- 처음 열어 보는 큰 폴더의 첫 헤더 읽기(서버 측 파싱 비용)는 줄일 수 없다 — 마우스 올림 미리 받기로 가린다.
- 서버를 재시작하면 캐시·풀이 비워져 첫 요청은 다시 느리다.

## 12. 공식 문서 확인 결과 (2026-10-02, 사용자 요청: "네이버 개발자센터에서 정확히 확인")
- **네이버 개발자센터 '네이버 오픈API 종류'** (https://developers.naver.com/docs/common/openapiguide/apilist.md) 를 직접 열어 확인: 로그인 방식 = 네이버 로그인·카페·캘린더 / 비로그인 방식 = 데이터랩·검색·이미지 캡차·음성 캡차·네이버 공유하기·네이버 오픈메인. **메일 읽기/보내기 API 는 없다.** 따라서 메일은 IMAP/SMTP 공식 프로토콜로만 가능하다(기존 결정 유지).
- 같은 목록에 쇼핑 검색(`/v1/search/shop`)이 있으나 이 프로젝트의 앱에는 미등록(SE05) — 기존 기록과 일치.
- **IMAP 동시 접속 수·발송 한도·유휴 연결 시간**: 네이버 고객센터에서 공식 문구를 찾지 못했다(고객센터 검색이 자동화 접속에서 막혀 화면을 읽지 못함). 사용자 지시("없으면 말고 IT 생태계 기준으로")에 따라 **일반적인 IMAP 클라이언트 관행**을 적용: 계정당 유휴 연결 3개 이하·45초 후 폐기·NOOP 확인, 실제 서버가 알려 준 값(`APPENDLIMIT=41943040`, 약 40MB)은 첨부 상한 25MB 설계의 근거로 유지.
- 서버 기능(CAPABILITY 실측): `IMAP4rev1 LITERAL+ SASL-IR ID CHILDREN UIDPLUS LIST-EXTENDED SPECIAL-USE UNSELECT QUOTA MOVE AUTH=PLAIN APPENDLIMIT=41943040` — MOVE·UIDPLUS(UID EXPUNGE)·SPECIAL-USE·UNSELECT 를 이 설계가 사용한다. `IDLE` 은 지원 목록에 없어 푸시 알림은 주기 확인(폴링)으로 해야 한다.
