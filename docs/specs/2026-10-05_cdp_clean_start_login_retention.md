# CDP 데몬 브라우저 — 깨끗한 시작 + 로그인 유지 기준서

작성 2026-10-05 · 창 gongmu-g2 · 상태: **구현·실검증 완료(로컬 커밋), 사용자 로그인 후 실계정 확인 대기**

## 1. 문제 (실측)
- 데몬이 Chrome 을 다시 띄울 때마다 어제 자동화가 열어 둔 YouTube·Gmail 탭이 되살아났다.
- 반대로 9222 Chrome 의 네이버 로그인 쿠키(`NID_AUT`·`NID_SES`)는 사라져 있었다(쿠키 이름 존재 여부만 확인).
- 원인 1: 데몬이 `--restore-last-session=false` 를 넘겼다. 이 스위치는 **값과 무관하게 있으면 켜진다**(Chromium 은 스위치 존재 여부만 본다) → 옛 탭 복원.
- 원인 2(실험으로 확인): 세션 쿠키(만료 없는 로그인 쿠키)는 이전 세션 복원 + **정상 종료**일 때만 재시작 뒤에도 남는다.

## 2. 실제 Chrome 비교 (임시 프로필·포트 9444·로컬 가짜 사이트가 세션 쿠키 발급, 사용자 9222 불사용)
| 경우 | 재시작 후 | 로그인 쿠키 |
|---|---|---|
| 복원 스위치 + **CDP `Browser.close`** | 탭 4개 복원 → 정리 후 빈 탭 1개 | **유지** |
| 기본 설정 + 정상 종료 | 복원 없음 | 사라짐 |
| 복원 스위치 + 종료 신호(Windows 창 닫기 요청) | 탭 4개 복원 | **사라짐** |
| 복원 스위치 + 강제 종료 | 복원 안 됨 | 사라짐 |
| Preferences 파일에 "이어서 열기"만 기록 | 복원 안 됨 | 사라짐(Chrome 이 변조 방지로 무시) |
- 결론: 로그인 유지는 **복원 스위치(값 없이) + CDP `Browser.close` 정상 종료**의 조합에서만 확인됐다. 종료 신호·강제 종료는 프로세스 정리용 안전망일 뿐 로그인 보존을 보장하지 않는다.

## 3. 공식 문서 확인 (개발자 센터·공식 자료)
- developer.chrome.com "Changes to remote debugging switches to improve security": Chrome 136 부터 `--remote-debugging-port` 는 **기본 프로필에서 무시**되고 별도 `--user-data-dir` 이 함께 있어야 한다 → 우리 실행 경로는 이미 별도 프로필(`data/cdp_profile/ai_chrome`)을 쓰며, 회귀 시험으로 고정했다. (자동화용으로는 Chrome for Testing 을 권장 — Google 로그인 차단 가능성이 있어 이번엔 보류.)
- ChromeDriver 릴리스 노트: 쿠키가 SQLite 에 올바르게 저장되도록 정상 종료를 도입(86), 136 에서 `quitGracefully` 로 `Browser.close` 또는 SIGTERM 을 SIGKILL 보다 먼저 시도 → 우리 종료 순서(CDP → 신호 → 강제)와 같다. 단 위 실측에서 신호 단계는 로그인을 보존하지 못했다.
- Chrome Enterprise `RestoreOnStartup`(마지막 세션): 세션 쿠키 소멸을 끄는 변조 방지 방식이나 **정책은 PC 전체 Chrome 에 적용**되어 사용자의 일반 Chrome 까지 "조직 관리"가 되므로 쓰지 않는다.
- 시작 사이트: **지정하지 않는다.** 빈 탭 `about:blank` 는 사이트가 아니라 정리 코드가 옛 탭을 닫기 전에 만드는 탭이다(Chrome 은 마지막 탭을 닫으면 종료). 사이트를 지정하면 불필요한 접속·이력만 생긴다.

## 4. 구현 (`scripts/browser_lifecycle.py`, L4 브라우저 엔진)
- `RESTORE_SWITCH = "--restore-last-session"` — 데몬(`cdp_daemon.py`)·`cdp_force_start.py` 실행 인자에 값 없이 추가. `=false` 표기 금지(회귀 시험).
- `close_stale_tabs(port)` — 시작 직후 복원된 옛 탭을 닫고 빈 탭 하나만 남긴다. 복원이 끝나기를 **탭 목록이 두 번 연속 같을 때까지**(최대 10초) 기다린다(고정 대기 폐기 — 탭이 많아도 정확). 사용자가 실행 중에 연 탭은 건드리지 않는다. 실패해도 브라우저 시작을 막지 않는다.
- `stop_browser(port, pid)` — 종료 3단계: ① CDP `Browser.close`(로그인 보존) ② 종료 신호 ③ 강제 종료. 데몬은 ①이 아닌 경로로 끝나면 "로그인 세션이 사라졌을 수 있다" 경고를 남긴다.
- 쿠키 값은 읽지도 바꾸지도 않는다(세션 보존 원칙). 로그인·로그아웃 동작 없음.

- 실제 데몬: 재시작 → Chrome 정상 종료 → 옛 탭 2개 정리 → 빈 탭 1개 확인.

## 6. 남은 확인(사용자)
- 사용자가 9222 Chrome 에서 네이버·구글에 한 번 로그인한 뒤, 데몬을 재시작해 쿠키 이름 존재 여부(참/거짓)로 유지 확인.
- 한계: 전원 차단·프로세스 강제 종료는 세션 쿠키를 잃을 수 있다.

## 7. 시작 페이지(홈) 고정 — 구글 (2026-10-05 사용자 요청)
- 요구: 데몬 브라우저를 켤 때 구글이 시작 화면으로 나오게 고정한다.
- 방식: Chrome 의 홈페이지·시작 설정은 변조 방지로 보호돼 Preferences 파일로는 고정되지 않았다(§2 실험). 그래서 데몬이 (재)시작 직후 옛 탭을 정리할 때 **빈 탭 대신 `CDP_START_URL`(= `GOOGLE_URLS["home"]` = `https://www.google.com/`) 탭 하나만 남긴다**(`close_stale_tabs(start_url=…)`). 주소는 `scripts/config.py` 에서 중앙 관리.
- 안전: 시작 주소는 `http(s)` 또는 `about:blank` 만 허용(그 밖의 스킴·공백·제어문자는 빈 탭으로 대체). 구글에 로그인하거나 동작하지 않고 첫 화면만 연다.
- 실측(임시 프로필·로컬 가짜 사이트를 시작 주소로 지정): 옛 탭 4개 복원 → 정리 → 시작 주소 탭 1개만 남음, 로그인 쿠키 유지.
- 한계: 사용자가 실행 중에 새 탭을 열 때의 "새 탭 페이지"·홈 버튼은 Chrome 보호 설정이라 바꾸지 않는다(데몬 (재)시작 때만 구글 시작 탭).
