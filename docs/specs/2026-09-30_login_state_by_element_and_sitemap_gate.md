# 로그인 상태를 "요소"로 판정 + 사이트맵 확인 게이트 — 기준서

- 날짜: 2026-09-30 / 상태: **v3 — 로그인 판정 정정(실제 화면 캡처로 확인), 사용자 승인 대기** / 기존 구현 확인: `scripts/login_detector.py`, `scripts/ops/write_gates/`(등록형 게이트 구조)
- 사용자 지시: 로그인은 **로그인 버튼(요소)을 찾아 판단**해야 한다 / **사이트맵을 탐지하는 훅을 설정**하라.

## 1. 실제 결함 (재현 확인)
`detect_login_state()` 의 사용자명이 블로그 피드의 글 본문 "…여배우 이청아 님도…" 에서 나옴 (`greeting: 이청아`, `user_block: null`).
원인: (7) "○○○님" 정규식이 **`document.body.innerText` 전체**를 검색. 로그인 여부(`logged_in`)는 logout 문구·링크로 맞게 나왔지만
**사용자명은 화면 아무 글에서나 뽑힘** → 파이프라인이 "다른 사용자 로그인"으로 오판해 자동 로그인 중단.
근본 원인은 "사이트마다 로그인/로그아웃 버튼이 어디 있는지"를 모르고 **범용 추측**(본문 전체 문구)을 한 것.

## 2. 변경 A — 요소 기준 판정 (사이트 프로필)
| 항목 | 내용 |
|---|---|
| 방식 | 사이트별 프로필(`configs/login_probes.json`)에 **로그인 버튼 / 로그아웃 버튼 / 계정 표시 영역**의 셀렉터를 둔다. 값은 `data/sitemap/*.json` 의 실제 텍스트·링크에서 뽑는다(예: 네이버 `"로그인하기"`, `nidlogin.login` 링크) |
| 판정 | 로그인 버튼 **보임** → 미로그인 / 로그아웃 버튼 **보임** → 로그인 / 둘 다 없음 → `unknown`(추측하지 않음) |
| 사용자명 | 프로필의 **계정 표시 영역 안에서만** 읽는다. 없으면 `user=None`. 본문 전체 정규식(7)은 프로필이 없는 사이트의 **보조 신호**로만 남기고 사용자명으로는 쓰지 않는다 |
| 파이프라인 | `user` 가 `None` 이면 "다른 사용자"가 아니라 **"확인 불가"**로 처리 — 로그아웃·중단하지 않고 계정 확인 경로(로그인 버튼 유무·프로필 요청)로 넘김 |
| 호환 | 반환 dict 의 키(logged_in, score, user, evidence)는 유지. 추가 키 `method`(element/heuristic), `state`(in/out/unknown) |
- 위치: 기존 `scripts/login_detector.py` 안에 함수 추가(새 파일 만들지 않음). 다른 사이트 호출자(google/auth 등)는 프로필이 없으면 **종전 동작 그대로**.

## 3. 변경 B — 사이트맵 확인 게이트 (훅)
기존 `prewrite_capability_check.py` 의 등록형 구조에 게이트 1개 추가: `tools/write_gates/sitemap_gate.py`.
| 항목 | 내용 |
|---|---|
| 발동 | 사이트 자동화 경로(`scripts/naver/`, `scripts/eum`, `scripts/browser_agent/`, `ai_orchestrator/connectors/`)의 .py 를 **작성/수정**하면서 내용에 셀렉터·로그인 판정 코드(`query_selector`, `locator(`, `login`, `logged_in`)가 있을 때 |
| 검사 | 코드가 다루는 도메인(내용/경로에서 추출)의 사이트맵 `data/sitemap/<도메인>*.json` 이 **있는지**, 있으면 이 세션에서 **읽었는지**(Read 기록). 없으면 "먼저 사이트맵을 수집하라"(수집 명령 안내) |
| 강도 | 처음엔 **경고만**(차단 아님) → 오탐률을 로그로 측정한 뒤 차단 승격 결정 |
| 로그 | `data/logs/sitemap_gate.jsonl` (발동/통과/경고, 파일·도메인) |
- 새 훅 파일이 아니라 기존 게이트 등록 1줄 + 게이트 모듈 1개. 훅 설정(`.claude/settings.json`) 변경 없음.

## 4. 드라이런 계획 (파일 수정 없이)
1. 실제 네이버 블로그 홈 화면에 새 판정을 임시로 돌려 `state`/`user` 확인 — 기대: `in`(로그아웃 버튼 존재)·`user=None`(오탐 `이청아` 사라짐).
2. 로그인 페이지(nidlogin)에서 기대: `out`. 
3. 프로필 없는 사이트(예: 구글 계정)에서 종전과 **완전 동일한 반환**인지 비교.
4. 사이트맵 게이트: 기존 파일 20개를 통과시켜 발동/경고 수와 오탐 후보 집계.

## 5. 테스트·검증
- 단위: 요소 있음/없음/둘 다 없음, 본문에 "○○님" 있어도 user=None, 프로필 없는 사이트 회귀, 파이프라인의 `None` 처리.
- 변이 시험: 판정 조건 뒤집기, 셀렉터 범위 확대 등이 테스트에 잡히는지.
- 실제 화면: 위 드라이런 1~3 을 자동화 테스트가 아닌 **실제 브라우저**로 확인(합성 HTML 만으로 통과 보고 금지).

## 6. 위험·한계
- 사이트맵이 낡으면 버튼 셀렉터가 어긋남 → `unknown` 으로 떨어지고 추측하지 않으므로 오판 대신 "확인 불가"가 된다.
- 사이트맵 수집물은 네이버 2개뿐 → 프로필은 네이버부터. 다른 사이트는 수집 후 추가.
- 아직 미확인: 네이버 로그아웃 버튼의 실제 셀렉터(피드 화면에서 확인 필요 — 드라이런 1에서 확정).

## 7. 되돌리기
커밋 revert. 게이트는 경고 모드라 개발 흐름을 막지 않음.

## v2 — "HTML 에서 정보를 수집하는 방식으로 강제" (사용자 지시, 2026-09-30)

### 원칙
셀렉터·로그인 판정 규칙은 **즉석 JS 탐색이나 추측이 아니라, `scripts/explorer/page_snapshot.snapshot()` 이 수집한 HTML 스냅샷**에서만 뽑는다.
이미 있는 수집·분석 계층(`page_snapshot`, `page_analysis`)을 그대로 쓰고 새 수집기를 만들지 않는다.

### 실제 화면 수집 결과 (네이버 블로그 홈, 312 요소, 6 프레임) — 이 결과가 설계를 바꾼다
| 사실 | 설계에 미치는 영향 |
|---|---|
| 로그아웃 요소 5개(버튼 2 + 링크 3), 내정보 보기, 내 블로그, 글쓰기 존재. 사용자 이름을 담은 요소는 없음 | 이 화면은 로그인 상태. 이름은 화면 요소에서 못 얻음 → `user=None` 이 정직한 값 |
| 로그아웃 **버튼 2개는 `visible: False`** (펼치는 메뉴 안) | "요소 존재"가 아니라 **보임 여부**로 판정해야 함. 숨은 요소는 근거에서 제외 |
| **링크에는 `visible` 필드가 없다**(버튼에만 있음). 로그인/로그아웃 대부분이 링크 | **수집 보강 필요**: 링크·입력에도 보임 여부 수집 (`page_snapshot`) |
| `login` 역할 요소(로그인, NAVER 로그인)가 로그인된 화면에도 존재 | 역할 분류만으로 상태 판단 금지. 보임 + 위치(헤더 영역) 필요 |
| 역할 분류표에 `logout`·`account`(내정보/내 블로그) 역할이 없음 | `page_analysis._BUTTON_ROLES` 에 `logout`, `account` 추가 (표 1줄씩, 우선순위는 `login` 뒤) |

### 변경 범위 확정
1. `page_snapshot.snapshot()`: 링크(a)·입력(input)에도 `visible` 수집 추가 (기존 키 유지, 키 추가만).
2. `page_analysis`: 역할 `logout`, `account` 추가. `analyze_snapshot` 의 요소에 이미 있는 `visible` 을 활용해 `login_state`(in/out/unknown) 계산 함수 추가:
   보이는 logout/account 존재 → in / 보이는 login 만 존재 → out / 그 외 → unknown. (순수 함수, 브라우저 접근 없음)
3. `scripts/login_detector.detect_login_state`: 프로필이 있는 사이트는 위 스냅샷 판정을 사용, 사용자명은 계정 영역 요소에서만. 프로필 없는 사이트는 종전 동작.
4. 프로필 `configs/login_probes.json`: **값은 스냅샷 JSON 에서 뽑은 것만** 허용.

### 강제 장치 (훅 + 테스트)
| 장치 | 내용 |
|---|---|
| 게이트(경고→차단 승격) | 사이트 자동화 코드에 셀렉터·로그인 판정을 쓰는 작성/수정 시, 그 도메인의 **스냅샷 파일**(`data/sitemap/<도메인>*.json`)이 없으면 "먼저 `snapshot` 으로 수집하라"고 안내. 첫 단계는 경고 |
| 테스트 | `configs/login_probes.json` 의 모든 셀렉터/문구가 **저장된 스냅샷 fixture 안에 실제로 존재**하는지 검사 — 스냅샷에 없는 값은 CI 에서 실패 (추측 셀렉터 유입 차단) |
| 회귀 fixture | 오늘 수집한 네이버 블로그 홈 스냅샷(글 본문에 "이청아 님" 포함)을 fixture 로 저장 → `user is None` 을 잠금 테스트 |
- fixture 는 개인정보 방지를 위해 **요소 라벨·역할·visible 만 남기고 글 본문/이름은 제거**한 축소본으로 저장(단, 오탐 재현용으로 "가짜 이름 님" 문자열은 합성값으로 대체).

## v3 — 정정: 이 화면은 로그아웃 상태였다 (사용자 지적, 화면 캡처로 확인)

### 정정할 오류 3가지
1. `detect_login_state` 가 **로그아웃 화면을 `logged_in=True`(score 8)로 판정**했다. 근거로 센 `logout_in_text`, `logout_link` 는 **숨은(visible=False) 요소**였다 — 화면에는 우측 상단 "로그인" 버튼, 우측 패널 초록 "NAVER 로그인" 버튼, 본문 "로그아웃 상태입니다"가 보인다.
2. 앞서 v2 에서 스냅샷을 보고 "로그인된 상태"라고 쓴 것도 **같은 실수**(숨은 로그아웃 요소를 보고 결론). 철회한다.
3. 그래서 자동 로그인 파이프라인이 "다른 사용자 로그인(이청아)"으로 멈춘 것은 **이중 오판**이었다. 실제로는 로그아웃 상태 → 자동 로그인을 진행했어야 했다.
- 교훈(CASE 후보): 화면 요소의 **존재**와 **보임**을 구분한다. 상태 판정은 눈에 보이는 근거와 **쿠키 같은 독립 신호**가 일치할 때만 확정한다.

### 판정 규칙 — 신호 4개를 각각 재고, 합의해야 확정
| 신호 | 로그인됨 | 로그아웃됨 | 비고 |
|---|---|---|---|
| S1 보이는 로그인 버튼 (`visible=True` 이고 뷰포트 안) | 없음 | **있음** | 헤더/패널 영역의 `login` 역할. 숨은 요소는 세지 않음 |
| S2 보이는 로그아웃/계정 요소 (`visible=True`) | **있음** | 없음 | 숨은 로그아웃(메뉴 안)은 세지 않음 |
| S3 세션 쿠키 (`NID_AUT` **and** `NID_SES`, 브라우저 컨텍스트 쿠키, 값은 읽지 않고 **존재만**) | **있음** | 없음 | httpOnly 라 페이지 JS 로는 못 봄 — Playwright `context.cookies()` 로 이름만 |
| S4 화면 문구 "로그아웃 상태입니다" 등 명시 문구 | 없음 | 있음 | 보조 |
- **결론:** S1·S2·S3 가 모두 한 방향 → `in` 또는 `out` 확정. **하나라도 충돌 → `unknown`** (추측하지 않는다).
- 오늘 화면 적용: S1=있음, S2=없음(보이는 것 없음), S3=없음, S4=있음 → **`out` 확정**. 기존 방식은 S2 를 숨은 요소로 채워 `in` 으로 오판.
- 쿠키 이름만 확인하고 **값은 읽지도 기록하지도 않는다**(세션 추출 금지 규칙 준수).

### 파이프라인 동작 (`naver_login_pipeline`)
| 판정 | 동작 |
|---|---|
| `out` | 저장된 계정으로 **자동 로그인 1회** 시도(캡차·인증이 뜨면 즉시 중단하고 사용자에게 요청) |
| `in` | 계정 확인: 계정 영역 요소로 이름을 읽어 목표 계정과 대조. 이름을 못 읽으면 `user=None` → "확인 불가"(로그아웃하지 않음) |
| `unknown` | 아무것도 바꾸지 않고 이유(어느 신호가 충돌했는지)를 보고 |
- 결과 dict 에 `evidence`(신호별 값)와 `state` 를 항상 포함 — 왜 그렇게 판정했는지 보이게 한다.

### 검증 계획 (실제 화면 3곳 + 잠금)
1. 지금 로그아웃 화면 → `out`, `user=None`
2. 로그인 성공 후 화면 → `in` (자동 로그인 1회 뒤 확인)
3. 로그인 페이지(nidlogin) → `out`
4. 구글 계정 화면 → 프로필 없음 → 종전과 동일 반환
5. 오탐 fixture: 오늘 스냅샷(숨은 로그아웃 + 보이는 로그인 + 본문 "○○○ 님")을 축소 저장 → `out`·`user is None` 잠금
6. 변이 시험: S1/S2/S3 조건 반전, "visible" 조건 제거가 테스트에 잡히는지
