# 홈택스 무인/준무인 연동 전략 (F-4G-3X)

> **작성일**: 2026-04-25
> **상태**: 설계/조사 문서 (코드 변경 없음)
> **선행 단계**: F-4F-2A(manual handoff observer), F-4G-1(controlled action plan), F-4G-3B(post-login smoke runner), F-4G-3E(warmup/retry)
> **목적**: 홈택스 자료 수집을 “대표님 수동 실행”에 의존하지 않으면서, 보안/약관/법령 위반 없이 자동화하는 현실적 경로를 다시 분류한다.

---

## 1. 결론 요약

### 1.1 한 줄 결론

홈택스 자료 수집은 **단일 경로(브라우저 자동화)에 몰빵하면 안 된다.** 자료별로 (a) 공식 API, (b) ASP/ERP 연동, (c) 세무대리 권한 위임, (d) 로컬 에이전트 브라우저 — 4가지 경로를 분리해서 매핑해야 한다.

### 1.2 “대표님 무실행” 구조의 핵심

| 항목                   | 현재 (F-4G-3B)                | 목표 구조 (F-4G-3X 이후)                            |
| ---------------------- | ----------------------------- | --------------------------------------------------- |
| 명령 실행 주체         | 대표님 (`python scripts/...`) | 서버 → 로컬 에이전트 (작업 큐, 폴링/WS)            |
| 브라우저 실행 주체     | 로컬 에이전트                 | 로컬 에이전트                                       |
| 인증값 입력 주체       | 대표님 (수동)                 | 대표님 (수동, 1회 또는 모바일 간편인증 승인만)      |
| 결과 확인 주체         | 대표님 (JSON/MD를 본인이 봄) | Claude (서버 업로드 결과를 직접 read)               |
| Claude 판정 가능 여부 | 결과를 사용자가 붙여넣어야 함 | 직접 판정 가능 (서버 결과 폴링)                     |

### 1.3 추천 우선순위

1. **TAX-API-1**: 공식 API로 대체 가능한 자료(사업자 상태조회/진위확인 등)부터 API 연동 PoC.
2. **TAX-ASP-1**: 전자세금계산서 매출/매입은 등록 ASP 또는 민간 API 업체 연동 검토.
3. **TAX-DELEGATE-1**: 세무대리/자료제공 동의가 가능한 자료는 권한 위임 구조 검토.
4. **F-4G-3Y**: 홈택스 화면이 꼭 필요한 자료만, 작업 큐 기반 무실행 로컬 에이전트로 처리.

## 2. 기존 F-4G 방식의 한계

### 2.1 코드 단의 정책 (이미 충분히 강함)

`local_agent/browser_manual_handoff.py`, `scripts/run_hometax_post_login_smoke.py`, `local_agent/site_adapters/hometax.py` 의 정책은 일관되게 다음을 **금지**한다:

- `page.click` / `page.fill` / `page.type` / `page.press`
- `page.keyboard.*` / `page.mouse.*`
- `page.set_input_files` / `page.select_option`
- 폼 `submit` / 파일 다운로드 / 보안프로그램 자동 설치
- ID / PW / 인증서 비밀번호 / OTP / 보안값 입력
- `cookies` / `storage_state` / `localStorage` / `sessionStorage`
- input value / textarea value 수집
- 사용자 기존 브라우저 프로필 / `--remote-debugging-port` / `--headless`

이 정책은 본 문서에서도 그대로 유지된다.

### 2.2 운영 단의 한계

코드는 안전하지만 **운영 흐름**은 다음을 요구한다:

1. 대표님이 터미널을 열어 `python scripts/run_hometax_post_login_smoke.py` 를 실행.
2. visible Chromium 가 뜨면 직접 로그인/인증서/보안프로그램/메뉴 이동.
3. `runs/local_agent/hometax_post_login_smoke_*.json` 파일 경로를 확인.
4. (필요 시) 대표님이 그 결과 JSON/MD 를 Claude 에 붙여넣기.

이 흐름은 대표님이 사실상 **운영자/엔지니어 역할**을 직접 수행해야 한다는 뜻이다. 본 F-4G-3X 의 목표는 1)/3)/4)를 제거하고, 대표님은 **2번(인증)** 만 (필요 시) 책임지도록 재설계하는 것이다.

### 2.3 본 단계에서 폐기되는 전제

- ❌ 대표님이 터미널/CLI 를 직접 호출한다.
- ❌ 대표님이 결과 JSON/MD 의 경로를 본다.
- ❌ 대표님이 결과를 채팅/이메일로 붙여넣어 Claude 에게 전달한다.

### 2.4 본 단계에서도 절대 폐기하지 않는 원칙

- ✅ AI 가 ID/PW/인증서 비밀번호/OTP/간편인증 값을 입력하거나 저장하지 않는다.
- ✅ 쿠키/session/localStorage/sessionStorage/storage_state 를 읽거나 내보내지 않는다.
- ✅ 보안 우회 / 캡차 우회 / 인증 우회를 하지 않는다.
- ✅ 홈택스 약관/보안정책 위반 가능성이 있는 방식은 “위험 방식”으로 분리한다.

### 3.1 자료별 “브라우저가 꼭 필요한가” 의 판단

- **API/공공데이터로 거의 완전히 대체 가능** → 1, 2번. 우선 API 화.
- **ASP/ERP 연동이 사실상 표준** → 3, 4, 11, 12번. 외부 시스템과 계약/연동.
- **세무대리 권한 위임이 가장 안전** → 7, 8, 9, 10, 13번. 자료제공 동의 기반.
- **마지막에 브라우저가 진짜 필요한 자료** → 5, 6번 (월별 카드매입/현금영수증을 회사 사업자번호 단위로 회수) 같이, API 가 없거나 권한 위임으로 대체가 어려운 일부.

이 판단의 핵심은 **“브라우저 자동화는 최후의 수단”** 이다. 그리고 그 “최후의 수단” 조차도, 본 문서의 7장 “로컬 에이전트 브라우저 방식” 정책 안에서만 동작한다.

## 4. 공식 API 가능성

### 4.1 공식 / 공공 채널 (우선)

다음 채널이 우선 검토 대상이다. **본 문서는 채널 존재 여부를 표시할 뿐, 실제 활용 신청/계약 절차를 거쳐야 한다.**

- 국세청 “사업자등록정보” 진위확인 / 상태조회 — 공공데이터포털 (`data.go.kr`) 또는 국세청 직접 제공으로 알려진 공식 API.
- 공공데이터포털의 국세청 관련 API 카탈로그 — 사업자번호 검증, 휴폐업 조회 등.
- 홈택스 “세무플랫폼” / 오픈API ISP 등 정부 차원의 자료개방 추진 — 단, 시점에 따라 진행 단계/범위가 달라지므로 **활용 시점에 다시 공식 안내를 확인할 것**.

### 4.2 민간 API 업체 (보조)

- 사업자번호 검증/세금계산서 발행/조회 SaaS 가 다수 존재하며, 이들이 홈택스/국세청과 자체 연동 인프라를 가지고 있는 경우가 일반적이다.
- 본 문서는 “민간 업체 X 가 가능하다”라는 식의 추천을 하지 않는다. 대신 **계약/SLA/약관/개인정보 처리** 관점의 비교를 거친 뒤 채택하라.

### 4.3 명시적으로 “공식 API 로 대체 불가” 인 자료

- 부가세 신고서 자체 제출, 원천세 신고 — 공식 API 가 아니라 “신고” 자체가 책임 동작이며, 일반적으로 사용자(또는 세무대리) 본인이 화면에서 마무리한다.
- 인증서 기반 “납부” / “이체” / “발행하기” — 자금/세무 동작이며 어떤 자동화 채널에서도 AI 가 단독 실행해서는 안 된다.

## 5. ASP/ERP/민간 API 가능성

### 5.1 전자세금계산서

- 다수의 ASP 가 발급/수취 데이터를 전자세금계산서 표준에 따라 처리하며, 회사가 등록 ASP 를 사용하면 “홈택스 화면에서 일일이 다운로드” 가 사실상 불필요해진다.
- 매출/매입 자료를 회계 시스템으로 직접 들여오기에 가장 자연스러운 경로.

### 5.2 회계/세무 ERP

- 회사 회계가 특정 ERP 위에 있다면, ERP 자체가 홈택스/은행/카드사 데이터를 받아오는 채널을 이미 보유하고 있는 경우가 많다.
- 이 경우 “홈택스 자동화” 보다 “ERP 데이터 추출 자동화” 가 더 현실적이고 안전하다.

### 5.3 공통 검토 포인트

- 비용 (월정액/건당)
- 자료의 시계열 보존 기간
- 회사 사업자번호별 분리 / 다사업자 처리
- API 인증 방식 (mTLS / Bearer / 키 기반)
- 약관 상의 “데이터 재사용” / “AI 학습 사용” 금지 여부

## 6. 세무대리 / 자료제공 동의 기반

### 6.1 구조

- 회사가 세무대리인을 지정하면, 세무대리인이 본인 인증서/계정으로 회사 자료를 합법적으로 조회할 수 있다.
- “자료제공 동의” 만 하면 회사는 본인 인증을 직접 하지 않고도 일부 자료를 세무대리인 채널로 흘려보낼 수 있다.

### 6.2 본 시스템에서의 의미

- AI / 로컬 에이전트가 “회사 대표님 본인의 인증서” 로 로그인하지 않아도, 자료의 상당 부분을 회수할 수 있다.
- 이는 **인증값을 AI 가 직접 다루지 않는다는 본 시스템의 핵심 원칙과 정합** 한다.

### 6.3 고려사항

- 세무대리 계약은 **법적/계약적 행위**이며, 코드/시스템이 임의로 만들어내는 것이 아니다.
- 대표님이 별도로 계약/위임/동의 절차를 거친 뒤, 그 결과로 **세무대리인 측 시스템** 또는 **자료제공 동의 기반 채널** 에서 자료가 흘러들어온다.
- 본 시스템은 그 자료를 “수신/저장/판정” 하는 쪽에 집중한다.

## 7. 로컬 에이전트 브라우저 방식 (대표님 무실행 구조 설계)

### 7.1 핵심 전제

- 대표님은 터미널을 열지 않는다.
- Claude / 서버가 작업을 생성하고, 로컬 에이전트가 그 작업을 받아 visible 브라우저를 띄운다.
- 인증이 필요한 순간에만 **OS 알림 / 화면 알림** 으로 대표님을 부른다.
- 인증은 대표님이 직접 한다 (모바일 간편인증 승인 또는 인증서 비밀번호 직접 입력 — AI 는 절대 만지지 않는다).
- 결과는 자동으로 서버에 업로드되고, Claude 가 직접 읽는다.

### 7.3 단계별 설계 항목

#### 7.3.1 작업 생성 API

- `POST /orchestrator/api/v1/tasks` (예시 경로 — 실제 경로는 기존 컨벤션과 정합 필요).
- 입력:
  - `site_key`: `"hometax"` 등.
  - `task_kind`: `"post_login_observe"`, `"download_plan"` 등 (실행 동사 아님 — observe / plan only).
  - `target_url`, `user_ready_seconds`, `max_text_chars`, `warmup_url`, `goto_retries` 등 (`scripts/run_hometax_post_login_smoke.py` 의 CLI 옵션 셋과 동등).
- 인증: 기존 orchestrator API 인증 정책에 종속.

#### 7.3.2 로컬 에이전트 작업 큐

- 두 가지 옵션:
  - (a) WebSocket 푸시 — 응답성↑, 운영 복잡도↑.
  - (b) 간단한 polling (예: 5~30초 간격) — 응답성↓, 운영 복잡도↓.
- 1차 PoC 는 **polling** 권장 — 구현/관측/장애복구 단순성 우선.
- 작업 상태: `queued → claimed → running → awaiting_user → captured → uploaded → done | failed`.

#### 7.3.3 visible browser 실행

- 기존 `local_agent/browser_manual_handoff.py::observe_after_user_ready` 를 그대로 재사용.
- 본 함수는 이미 `headless=False` 로 동작한다.

#### 7.3.4 “인증 승인 필요” 알림

- 로컬 에이전트가 작업을 받으면:
  - Windows 토스트 알림 또는 시스템 트레이 풍선.
  - 화면 모달이 아니라 OS 알림 (사용자가 다른 일을 할 때 방해 최소화).
- 알림 메시지 예: “홈택스 post-login observe 작업이 시작됩니다. 브라우저에서 로그인을 마쳐주세요. (남은 대기: 120초)”.
- 대표님 입장에서의 동작은 “브라우저 → 로그인” 하나뿐이다.

#### 7.3.5 인증 완료 감지 (자동 클릭/입력 없이)

- 본 단계에서도 **완벽한 자동 감지는 시도하지 않는다.**
- 현재 구현된 흐름 그대로 사용:
  - `observe_after_user_ready(user_ready_seconds=...)` 가 N 초 sleep 후 한 번 read-only 캡처.
  - “페이지 분류” (`classify_hometax_page`) 가 `authenticated` / `download_page` / `unknown` 등을 알려준다.
- 향후 확장: 동일 URL 에서 여러 차례 read-only 폴링하여 page_state 가 `login_required` → `authenticated` 로 바뀌었는지 판단 (단, 어떤 클릭/입력도 없이 read-only 만).

#### 7.3.6 read-only observer

- 그대로 재사용.

#### 7.3.7 controlled plan 생성

- 그대로 재사용 (`build_hometax_controlled_action_plan`).

#### 7.3.8 결과 업로드

- `POST /orchestrator/api/v1/tasks/{task_id}/result` 로 JSON/MD 페이로드 업로드.
- 업로드 페이로드는 현재 `scripts/run_hometax_post_login_smoke.py::build_result_payload` 가 만드는 구조와 동일.
- 인증서/쿠키/스토리지/HTML 원문은 페이로드에 포함되지 않는다 (현 정책 그대로).

#### 7.3.9 실패 원인 자동 분류

- 기존 `summary.success` + `verdict (PASS/WARN/FAIL)` 를 그대로 사용.
- 추가:
  - `awaiting_user_timeout` (대표님이 user_ready_seconds 안에 로그인 마치지 못한 경우).
  - `forbidden_env_present` (코드 단의 환경변수 가드가 차단).
  - `goto_failed` (warmup/retry 후에도 실패).

#### 7.3.10 감사 로그

- 작업 ID / 시작/종료 / verdict / 페이지 분류 결과 / warning 만 기록.
- 인증값 / 쿠키 / 스토리지 / 페이지 HTML 원문은 절대 기록하지 않는다.
- 기존 `ai_orchestrator/audit_logger.py` 와 정합되도록 설계.

### 7.4 본 단계에서 자동화하지 않는 것

- 대표님이 인증서 비밀번호를 입력하는 행위.
- 대표님이 모바일 간편인증을 승인하는 행위.
- 보안프로그램(AhnLab/INISafe/MagicLine/TouchEn 등) 설치/실행.
- 인증 후 자료 다운로드 “버튼 클릭” — 본 단계에서는 plan 만 만든다.

### 7.5 “기존 Chrome 프로필 / 세션 재사용” 검토 — **불가/위험**

- Playwright 의 `--user-data-dir` 또는 `storage_state` 로 기존 세션을 재사용하면 인증 부담이 줄지만, 다음 이유로 **본 시스템은 채택하지 않는다.**
  - 정책상 `cookies` / `storage_state` 접근 금지.
  - 사용자 다른 웹사이트(메일/금융/SNS) 세션이 같은 프로필에 남아있을 수 있어 정보 노출 위험.
  - 홈택스 보안프로그램이 프로필 핸들 변경을 탐지해 차단할 가능성.
- 대안: **매번 fresh context** + 대표님이 인증을 다시 한다 (단, 모바일 간편인증이면 부담이 작다).

## 9. 추천 아키텍처

### 9.1 우선순위 (재진술)

1. **TAX-API-1 (1순위)** — 공식 API / 공공데이터로 대체 가능한 자료부터 API 화.
   - 대상: 사업자 상태조회, 진위확인 등.
   - 인증: API 키.
   - AI 판정 가능 여부: 즉시 가능.

2. **TAX-ASP-1 (2순위)** — 전자세금계산서 등 ASP/ERP 표준 채널.
   - 대상: 매출/매입 (전자)세금계산서, 회계 데이터.
   - 인증: 회사 ASP 계약 + API 키 / 회사 ERP 사용자 인증.
   - AI 판정 가능 여부: ASP/ERP 가 제공하는 export 형식에 따름.

3. **TAX-DELEGATE-1 (3순위)** — 세무대리 권한 / 자료제공 동의.
   - 대상: 부가세 신고서/매출매입 합계, 납세증명, 소득증명, 원천세 등.
   - 인증: 세무대리인 본인 인증서 (회사 대표님이 직접 만지지 않음).
   - AI 판정 가능 여부: 세무대리인 측 자동화 시스템 또는 자료 수신 채널에 따름.

4. **F-4G-3Y (4순위, 폴백)** — 작업 큐 기반 무실행 로컬 에이전트 브라우저.
   - 대상: 위 1~3 순위로 회수 불가능한 자료(현금영수증/카드매입/일부 명세).
   - 인증: 대표님 1회 로그인 (가능하면 모바일 간편인증).
   - AI 판정 가능 여부: 결과 JSON 을 서버 통해 자동 전달 받아 즉시 가능.

### 9.2 본 시스템에서 “브라우저 자동화” 의 위치

- **마지막 폴백** 으로만 사용한다.
- 폴백 이라도 정책은 동일: read-only / 클릭 입력 금지 / 쿠키 금지 / secret 금지.
- 대표님 입장에서의 부담은 “화면에서 로그인만 한다” 하나로 한정된다.

## 10. 다음 개발 단계

### 10.1 권장 단계 분기

본 단계(F-4G-3X) 이후, 두 갈래 중 하나를 채택할 수 있다.

#### 10.1.1 F-4G-3Y — 로컬 에이전트 작업 큐 기반 hometax smoke 실행 구조 설계

- 7.3 의 컴포넌트들을 단계적으로 구현.
- 1차 PoC 는 polling 기반.
- 기존 `scripts/run_hometax_post_login_smoke.py` 와 동등한 결과 페이로드를 서버로 업로드.
- 대표님은 더 이상 터미널을 열지 않는다.

#### 10.1.2 TAX-API-1 — 국세청/공공데이터 API 우선 연동 PoC

- 사업자 상태조회 / 진위확인 API 를 PoC 대상으로 잡는다.
- API 키 등록 → secret store 저장 → 정해진 호출 표준 → 결과 캐시 → 응답 시간/오류율 관측.
- 본 PoC 가 성공하면 동일 패턴으로 추가 자료를 API 화한다.

### 10.2 본 문서의 한계

- 특정 민간 업체 / 특정 ASP / 특정 세무대리 시스템에 대한 비교는 본 문서 범위에 포함되지 않는다.
- “공식 API 가능성” / “공공데이터 가능성” 은 본 조사 시점의 합리적 추정이며, 실제 채택 전 공식 신청/계약 절차에서 다시 확인되어야 한다.
- 본 문서는 코드 변경을 동반하지 않는다. 코드 단의 정책(`browser_manual_handoff` / `controlled_site_executor` / `hometax` site adapter)은 그대로 유지되며, 본 문서는 그 위에서의 **운영 흐름과 자료 분류** 만을 정한다.

## 부록 A. 본 문서의 “PASS / WARN / FAIL” 자가 판정

본 문서는 다음 조건을 만족한다.

- **PASS 조건**
  - [x] 자료별 추천 경로가 분리됨 (3장 표).
  - [x] 대표님 수동 실행 없는 구조가 설계됨 (7장 7.1 / 7.2 / 7.3).
  - [x] 금지 방식과 허용 방식이 명확히 분리됨 (8장 표).
- **WARN 조건**
  - [ ] 일부 자료의 공식 API 존재 여부가 “시점/공식 안내 재확인 필요” 로 남아있음 — 본 문서는 이를 명시(4.1 / 10.2).
  - [ ] 민간 API / ASP / 세무대리 후보군에 대한 구체적 업체 비교는 후속 작업에서 진행해야 함.
- **FAIL 조건 — 모두 회피됨**
  - [x] 대표님 수동 실행을 전제하지 않는다.
  - [x] AI 의 인증값 자동 입력/저장을 제안하지 않는다.
  - [x] 쿠키/session 추출 방식을 제안하지 않는다.

따라서 본 문서의 자가 판정은 **PASS (with WARN)** 이다.
